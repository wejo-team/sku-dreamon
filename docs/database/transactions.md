# 트랜잭션과 조회 일관성

**상태: 구현 전 처리 설계.** 정책은 [팀 모집](../specs/team-recruitment.md), [프로필](../specs/profile.md), [알림](../specs/notifications.md)에 두고, 여기서는 여러 테이블이 함께 지켜야 하는 저장 경계를 정의합니다.

## 공통 잠금 순서

기본 격리 수준은 PostgreSQL `READ COMMITTED`로 제안합니다. 정원·소속·지원 상태를 바꾸는 경로는 아래 순서를 공유합니다.

1. 변경 대상 사용자들의 `accounts` 행을 UUID 순서로 `FOR NO KEY UPDATE`.
2. 공개 여부·완성도를 확인해야 하면 해당 `profiles` 행.
3. 관련 `contests` 행을 UUID 순서로 `FOR SHARE`.
4. 변경할 `teams` 행을 UUID 순서로 `FOR UPDATE`.
5. 관련 `applications` 행을 UUID 순서로 `FOR UPDATE`.
6. 소속·상태 발생 건·알림을 기록하고 한 번에 commit.

권한 확인을 위해 읽은 팀장 계정까지 무조건 잠그지는 않습니다. “변경 대상 사용자”는 접수·검토 시작·선발·미선발·취소되는 지원자, 팀 생성 시 팀장입니다. 여러 사용자를 다루는 처리는 전체 대상 계정을 먼저 같은 순서로 잠급니다. 잠금을 얻은 뒤 대상·현재 버전·상태·시각을 다시 확인합니다.

마감 검사는 잠금 대기 이후의 실제 서버 시각으로 수행합니다. PostgreSQL의 트랜잭션 시작 시각인 `now()`를 현재 시각으로 오인해 대기 중 지난 마감을 통과시키지 않습니다.

아직 소속 행이 없는 사용자를 두 팀장이 동시에 선발할 수 있으므로 소속 행 잠금만으로는 충분하지 않습니다. 공통 계정 행을 먼저 잠가 같은 사용자의 팀 생성·지원 접수·지원 상태 변경을 직렬화합니다. 이는 초기 설계를 단순하게 하기 위한 선택이며, 서로 다른 공모전의 같은 사용자 변경도 잠시 직렬화됩니다.

계정 ID는 불변이므로 이 직렬화에는 `FOR NO KEY UPDATE`를 사용합니다. 같은 계정의 업무 요청끼리는 충돌하지만, 알림 수신자 등 계정 FK 검사에 필요한 `FOR KEY SHARE`는 허용합니다. `FOR UPDATE`를 쓰면 서로 다른 공모전의 팀장 A·B가 상대 팀에 동시에 지원할 때 각자의 계정 잠금과 상대 팀장 알림의 FK 검사가 순환 대기할 수 있습니다. 계정 FK를 참조한다는 이유만으로 상대 팀장 계정까지 추가로 독점 잠그지 않습니다. 계정 키 변경·삭제 기능을 도입할 때는 그 별도 경로의 잠금·참조 처리도 다시 검토합니다.

공고 공유 잠금은 동시 지원끼리는 허용하면서 처리 중 공고 조건 변경을 방지합니다. 공고 수정 경로를 추가할 때도 역순으로 계정·팀 잠금을 잡지 않아야 합니다. 조건 변경이 기존 기록에 미치는 정책은 별도 TBD입니다. [PostgreSQL 잠금 문서](https://www.postgresql.org/docs/17/explicit-locking.html)

## 쓰기 작업의 경계

| 작업 | 같은 트랜잭션에 포함할 것 | 실패 시 |
| --- | --- | --- |
| 프로필 저장 | 계정·프로필 잠금, 버전 확인, 본문·선택지·포트폴리오 전체 반영, 버전 증가 | 기존 프로필·연결 행 유지 |
| 신규 지원·허용된 재지원 | 현재 공개·필수 정보·모집 조건, 같은 공모전 소속·같은 팀 미선발 이력 확인, 새 지원 시도, 최초 상태 사건, 본인·팀장 알림 | 지원·사건·알림 모두 생성하지 않음 |
| 팀 생성 | 공고 조건·목표 정원·소속 확인, 팀·모집 역할·팀장 소속 생성, 같은 공모전 본인의 다른 대기 지원 폐기와 각 사건·알림·버전 증가 | 팀·소속·폐기·사건·알림 모두 이전 상태 유지 |
| 검토 시작·미선발 | 현재 팀장 권한·지원 버전·허용 전이 확인, 지원 상태·버전 갱신, 사건과 정책에 따른 알림 | 지원·사건·알림 모두 이전 상태 유지 |
| 선발 | 대상 선발, 확정 소속, 다른 대기 지원 폐기, 각 사건·알림, 관련 버전 증가, 정원 도달 시 팀 모집 마감 | 일부 선발·폐기·알림만 남기지 않음 |
| 본인 취소 | 지원 취소, 선발 상태였다면 소속 종료, 사건·알림, 관련 버전 증가 | 지원·소속 모두 이전 상태 유지 |
| 모집 재개 | 현재 기한·잔여 정원 검사, 팀 상태·사유·버전 갱신 | 이전 모집 상태 유지 |
| 알림 읽음 | 소유자 확인, 지정된 알림의 최초 `read_at` 저장 | 지정 집합 전체를 이전 상태로 유지 |

검토 시작·미선발은 명시적 팀장 명령이며 조회·모집 종료·기한 경과·정원 충족으로 자동 실행하지 않습니다. 팀 상태는 `open`·`closed`만 사용합니다. 팀장 선발 취소·강퇴·팀장 탈퇴·팀 삭제는 MVP 범위 밖이며, 일반 상태 수정으로 허용하지 않습니다. 범위와 남은 결정은 [팀 명세](../specs/team-recruitment.md#application-transitions)와 [결정 기록](decisions.md#open-decisions)을 따릅니다.

## 신규 지원·재지원·검토 처리

신규 접수는 계정·프로필·공고·팀 순서로 잠근 뒤 현재 공개·필수 정보·모집 조건을 확인합니다. 같은 공모전의 활성 소속이 있거나 같은 팀의 `rejected` 이력이 하나라도 있으면 거부합니다. `canceled`·`discarded` 이력은 새 시도를 막지 않지만, 새 접수 시점의 조건을 면제하지 않습니다. 같은 팀의 현재 유효 지원은 부분 UNIQUE 제약으로도 막습니다.

미선발 이력 조회는 `ix_applications_rejected_history`를 사용하고, 접수와 미선발 처리 모두 해당 지원자의 계정 잠금을 먼저 얻습니다. 따라서 미선발 처리와 새 접수의 경합이 이력 검사를 통과해 잘못된 재지원으로 이어지지 않습니다. 새 지원을 생성하더라도 이전 종료 지원·사건은 변경하지 않습니다.

검토 시작·미선발은 계정·공고·팀·지원 순서로 잠근 뒤 현재 팀장과 지원 버전을 확인합니다. 검토 시작은 `submitted → reviewing`, 미선발은 `submitted`/`reviewing → rejected`만 실제 전이로 허용합니다. 종료된 `rejected`·`canceled`·`discarded`의 다른 상태로의 변경은 거부합니다. 현재 버전으로 이미 같은 목표 상태를 요청한 경우는 아래 재시도 규칙에 따른 변경 없는 성공이며, 새로운 사건·알림을 만들지 않습니다.

## 팀 생성과 다른 대기 지원 폐기

1. 생성자의 계정을 잠그고 같은 요청 ID의 기존 성공 여부를 확인합니다. 새로운 생성이면 필요한 기존 프로필 확인·잠금 후 공고를 잠그고, 같은 공모전 활성 소속과 현재 생성 조건을 확인합니다. 이 순서는 [팀 생성의 프로필 완성 범위](../specs/profile.md#open-questions)를 새로 확정하지 않습니다.
2. 생성자의 같은 공모전 `submitted`·`reviewing` 지원을 모아 기존 팀 전체를 UUID 순서로 잠근 뒤, 해당 지원들을 UUID 순서로 잠급니다. 다른 공모전과 종료 지원은 대상에서 제외합니다. 같은 계정의 신규 지원·선발도 계정 잠금을 따르므로 대상 집합에 중간 삽입이 일어나지 않습니다.
3. 잠금 이후 조건·시각·상태를 다시 검증하고 새 팀·모집 역할·팀장 소속을 생성합니다. **기존 팀·지원의 잠금을 모두 얻은 뒤** 새 팀을 삽입하며, 새 팀 삽입 뒤에 기존 팀·지원 잠금을 역순으로 추가 획득하지 않습니다. 새 팀은 commit 전 다른 요청에 공개되지 않는 새 ID이므로 기존 팀 집합의 잠금 순서를 깨지 않습니다.
4. 수집한 대기 지원만 `discarded`로 변경하고 각각 버전·사건·알림을 기록합니다. `reason_code = team_created_elsewhere`, `cause_membership_id = 새 팀장 소속 ID`로 원인을 남깁니다. 원인 소속의 계정·공모전·팀장 역할과 다른 팀 여부를 검증합니다.
5. 정원이 1명이면 `closed + capacity_reached`도 함께 저장하고 한 번에 commit합니다. 실패하면 새 팀·소속과 기존 지원 폐기를 모두 rollback합니다. 같은 생성 요청의 재전송은 기존 팀을 반환하며 폐기를 다시 실행하지 않습니다.

다른 팀의 선발과 팀 생성이 경합하면 같은 계정 잠금·공모전 활성 소속 UNIQUE를 통해 먼저 성공한 작업만 소속을 만듭니다. 뒤의 작업은 잠금 이후 조건을 다시 확인해 충돌로 끝납니다. 팀 생성에 따른 폐기는 취소나 미선발로 바꾸어 기록하지 않습니다.

## 선발 처리

1. 지원 ID로 대상 계정·공모전을 식별하고 계정·공고 순서까지 잠급니다. 이 단계에서는 팀을 먼저 잠그지 않습니다.
2. 해당 계정의 대상 지원과 같은 공모전의 폐기 대상 지원을 조회하여 **대상 팀을 포함한 전체 팀 ID 집합**을 만듭니다. 이 집합의 첫 팀부터 UUID 순서로 잠그고, 그 뒤 지원들을 UUID 순서로 잠급니다. 같은 계정의 신규 접수도 계정 잠금을 따르므로 수집 도중 새 대기 지원이 끼어들지 않습니다.
3. 잠금 이후 현재 팀장 권한, 지원 상태, 소속 유무, 팀 정원과 버전을 다시 확인합니다. [선발 기한](../specs/team-recruitment.md#selection-window)에 따라 실제 서버 시각이 공고 접수 마감보다 이르고 여석이 있어야 합니다. 팀 `closed`·팀 모집 기한 경과는 기존 지원의 선발을 막는 조건이 아닙니다. 명세에 없는 학사·역할 조건을 선발 거부 조건으로 추가하지 않습니다.
4. 선택된 지원을 갱신하고 `team_memberships`를 생성합니다. 공모전별 활성 소속 UNIQUE 인덱스가 마지막 중복 방어선입니다.
5. 해당 사용자의 같은 공모전 다른 `submitted`·`reviewing` 지원만 폐기합니다. 선발 사건과 각각 다른 사건 ID를 발급하고 `reason_code = selected_elsewhere`, `cause_event_id`로 선발 원인을 연결합니다. 다른 공모전·종료 지원은 변경하지 않습니다.
6. 현재 소속 수가 정원에 도달하면 팀의 마감 상태·사유도 저장합니다. 선발·폐기 사건의 알림과 함께 commit한 뒤 성공 응답을 보냅니다.

모든 소속 변경이 팀 잠금을 따르므로 “빈자리 1개를 서로 다른 두 지원자에게 배정”하는 경쟁도 방지합니다. 소속 COUNT만 먼저 읽고 나중에 별도 트랜잭션에서 추가하는 방식은 사용하지 않습니다.

## 취소·자리 반환·재시도

본인 취소는 공고·팀 마감과 무관하게 `submitted`·`reviewing`·`selected`에서 허용합니다. `selected`였다면 지원과 활성 소속을 함께 변경합니다. 자리가 반환되어도 팀 상태를 자동으로 `open`으로 바꾸지 않습니다. 이전에 폐기된 지원도 변경하지 않습니다. 이후 모집 재개는 별도 사용자 명령입니다. 이미 `rejected`·`discarded`인 지원을 취소로 덮어쓰지 않습니다.

API는 수정할 리소스의 `expectedVersion`을 받습니다. 버전 불일치·현재 조건 충돌은 409로 구분하고 최신 리소스를 다시 조회하도록 안내합니다. 취소·폐기 후 허용된 재지원은 별도 사용자 행동이므로 새 지원 UUID와 새 요청 ID를 사용합니다. 미선발 이후 같은 팀의 재지원은 허용하지 않습니다.

버전을 먼저 비교하고, 일치한 상태에서 이미 같은 값인 경우에만 변경 없는 성공으로 응답합니다. 응답 유실 뒤 예전 버전으로 재전송했다면 현재 값이 같아도 409 후 다시 조회합니다. 이 규칙은 모집 종료·재개나 공개 전환의 이전 회차를 새 명령으로 오인하지 않게 합니다.

이미 성공한 **같은 명령의 재전송**과 **새로운 사용자 행동**은 구분해야 합니다. 생성 요청의 중복 식별과 재전송 응답은 [API 공통 계약](../api/conventions.md), 컬럼·유일 제약은 [팀·지원 테이블](teams.md)을 따릅니다. 단순 상태 재저장으로 새로운 사건·알림을 만들지 않습니다.

DB 교착·직렬화 충돌은 전체 트랜잭션을 rollback합니다. 재시도하더라도 처음부터 현재 상태·권한·기한을 확인하며, 재시도 횟수·대기 간격은 운영 구현에서 정합니다. 유일 제약 실패를 서버 내부 오류나 성공으로 감추지 않고 해당 도메인 충돌로 매핑합니다.

팀 생성·신규 지원·선발·미선발의 경합, 잠금 대기 중 마감 경계, 잘못된 폐기 원인은 [구현 시 검증할 사례](decisions.md#verification-cases)에서 관리합니다. 이 검증 계획은 실제 PostgreSQL 구현 후 확인하며 문서 변경 자체가 실행 성공을 뜻하지 않습니다.

## 목록과 총원

페이지 번호 목록의 행과 `total`은 **동일한 필터·권한·DB 스냅샷**에서 계산합니다. 한 SQL 문장으로 조회하거나 읽기 전용 `REPEATABLE READ` 트랜잭션을 사용합니다. 목록에서 제외한 비공개 프로필을 총원에 포함하지 않습니다.

정렬 키 뒤에는 고유 ID를 마지막 기준으로 둡니다. 별도 요청으로 다음 페이지를 읽는 동안 다른 사용자가 데이터를 바꾸면 페이지 구성·총원은 달라질 수 있습니다. 페이지 번호 방식이 여러 요청 전체의 고정 스냅샷을 제공한다고 약속하지 않습니다.

공고의 접수 상태, 팀의 신규 지원 가능 여부, 현재 소속 수, 연결 팀 수는 원본 데이터로 계산합니다. 표시용 카운트를 독립적인 진실로 저장하지 않습니다. 세부 필터·정렬·빈 페이지 응답은 [API 계약](../api/conventions.md)에 둡니다.

## AI 호출 경계

허용된 현재 데이터와 사용한 프로필 버전을 조회한 뒤 DB 트랜잭션을 종료하고 모델을 호출합니다. 외부 응답을 기다리는 동안 선발·프로필 잠금을 유지하지 않습니다.

응답 제공 시 현재 요청자·지원 관계·공개 범위·지원 상태를 다시 확인합니다. 프로필 버전이 달라진 결과를 최신 근거로 표시하지 않습니다. 검토 결과의 열람 권한과 새 선발 후보의 적격 상태는 구분합니다. AI 결과를 받아 실제 선발을 자동 수행하지 않으며, 저장·재검증·복사 계약은 [AI API](../api/ai-notifications.md)에 둡니다.
