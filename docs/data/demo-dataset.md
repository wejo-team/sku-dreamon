# 시연 데이터 제작과 운영

개발 데이터셋은 실제 공모전을 탐색하고, 서로 다른 공모전의 팀을 추천받아 지원한 뒤 팀장 관점에서 검토하는 흐름을 보여 주기 위한 자료입니다. 실행 대상은 로컬 `wejo_dev`입니다. 제품의 [추천 정책](../specs/matching.md)이나 [팀 모집 정책](../specs/team-recruitment.md)을 시연 때문에 완화하지 않습니다.

제작 규칙의 현재 버전은 **2.1.1**입니다. [버전 이력](versions.md)에 적용 상태와 검증 집계를 남기며, 제작 실행의 원본은 [시드 명령](../../backend/scripts/seed_dev_data.py), 공모전 선정·분배의 원본은 [분배 계획 코드](../../backend/scripts/dev_dataset.py)입니다.

## 입력 데이터와 보관 위치

| 자료 | 관리 방법 |
| --- | --- |
| 실제 공모전 | 기존 개발 DB의 공고·분야·참가 대상·출처를 재사용 |
| 가상 사용자 | 기존 `devuser001`~`devuser300`과 프로필·학사 연결을 재사용; 없는 계정만 생성 |
| 가상 팀과 지원 이력 | 고정된 시드 팀 ID를 사용해 제작; 재구성 시 지원·소속·상태 사건·알림도 함께 생성 |
| 제작 코드와 규칙 | Git의 `backend/scripts/`와 `docs/data/`에서 관리 |
| 원본·가공본·보고서·백업 | Git에서 제외된 `data/`에 로컬 보관 |

기존 공모전 수집 원본은 `data/raw/국내_공모전_500건_2026-10-26.json`, 가공본은 `data/processed/contests_db_2026-10-26.json`입니다. 500건 중 접수 날짜 등이 불명확한 10건을 제외한 490건이 기존 개발 DB에 적재되어 있습니다. 파일이 없는 새 환경에서는 기존 데이터 보관자로부터 해당 자료나 개발 DB 백업을 별도로 받아야 합니다. Git clone과 팀 시드 실행만으로 실제 공모전 490건이 복원되지는 않습니다.

공모전 원문·일정·참가 인원·공식 확인 상태는 팀 시드가 바꾸지 않습니다. `unknown`인 인원 제한을 임의로 제한 없음으로 바꾸거나, 마감된 실제 공모전의 날짜를 미래로 연장하지 않습니다. 신규 공고의 적재는 [공고 CLI](../api/contests.md#contest-import-cli)의 별도 작업입니다.

## 공모전 선정과 팀 분산

1. 기준 시각에 접수가 시작됐고 마감까지 **최소 7일** 남은 공모전을 고릅니다. 참가 인원은 `range` 또는 `unlimited`로 확인되어 있어야 하며, 3명 이상 팀을 구성할 수 있어야 합니다. 모든 팀의 목표 정원은 실제 공고의 최솟값·최댓값을 준수합니다.
2. 후보에서 분야가 다양한 공모전을 먼저 확보하고, 등록이 최신인 공모전과 마감이 여유로운 공모전을 함께 선택합니다. **21일 이상** 남은 공고를 장기 시연에 우선 활용합니다. 등록 시각이 같으면 공고 ID로 순서를 고정합니다.
3. 최대 **25개 공모전**을 선택하고 팀을 두 개씩 한 쌍으로 배정합니다. 선택한 공모전을 순환한 뒤 다음 쌍을 배정하므로 팀 최신순에서도 여러 공모전이 섞입니다.
4. 목표는 **100개 팀**, 한 공모전의 상한은 **6개 팀**입니다. 후보가 부족하면 팀 수를 줄이고 보고서에 경고를 남깁니다. 100개를 맞추기 위해 소수 공모전에 과도하게 몰아넣지 않습니다.
5. 각 쌍의 두 번째 팀은 모집 중인 지원 시연 대상으로 남깁니다. 첫 번째 팀에 정원 충족·팀장 종료·선발 후 취소를 나누어 배치합니다. 여러 상태를 보여 주면서도 공모전마다 새 지원 후보를 유지합니다.

팀 소개와 모집 역할은 연결된 공모전의 제목·분야에 맞춥니다. IT·창업 분야에는 개발 역할과 기획·디자인·마케팅·자료조사·발표 중 한 역할을 조합합니다. 디자인·영상 분야는 이 다섯 역할을 순환하고, 그 밖의 분야나 분야 미분류 공고는 기획·자료조사·발표를 순환합니다. 소개에 역할별 **팀이 제안하는 작업**을 적어 공고의 공식 요구사항과 구분하며, 모든 공모전에 동일한 캠퍼스 서비스 소개를 붙이지 않습니다.

가상 팀 표시는 `[시연용 가상팀]`을 사용합니다. 모든 소개에 `개발용`을 붙이면 AI의 `개발` 검색에 비개발 팀까지 포함됩니다. 표시 문구가 특정 역할 검색어를 오염시키지 않도록 하며, 현재 AI의 구조화 역할 코드 필터와 탐색 화면의 역할명 자유 검색을 각각 진단합니다.

팀 모집 기한은 제작 기준 시각에서 28~42일 뒤를 목표로 하되 공고 접수 마감을 넘지 않으며, 실시간 정책 검사 결과가 항상 최종 기준입니다.

2026-10-31 실제 적재에서는 이 조건을 만족한 **22개 공모전에 100개 팀을 4~6개씩** 배정했습니다. 분야가 등록된 18개와 분야 미분류 4개를 포함합니다. 분야가 없어도 접수·인원 조건을 충족하면 대상이 되며, 분야를 임의로 채우지 않습니다. 초기 조사에서 분야 연결이 있는 공고만 집계한 18개를 전체 후보 수로 사용하지 않습니다. 날짜와 입력 공고가 바뀌면 이후 실행의 후보 수와 팀 수도 달라집니다.

## 계정과 상태 시나리오

계정 이름·경력은 가상이고 포트폴리오는 `example.com` 예시입니다. 개발용 로그인 방법은 [로컬 실행](../development/local-development.md)에 있습니다. 기존 프로필의 공개 여부와 입력 내용은 재구성으로 초기화하지 않습니다.

| 계정 | 시연 역할 |
| --- | --- |
| `devuser001`~`devuser100` | 고정 팀 ID에 대응하는 팀장; 팀 수가 줄면 실제 생성된 팀장만 사용 |
| `devuser101`~`devuser298` | 공개 프로필인 계정에서 지원자를 선택해 지원·선발·취소 이력 생성 |
| `devuser299` | 기본 공개 프로필의 탐색·신규 지원용 계정; 자동 지원·선발에서 제외 |
| `devuser300` | 기본 비공개 프로필의 공개 전환 흐름 확인용 계정; 자동 지원·선발에서 제외 |

지원 상태는 `submitted`, `reviewing`, `selected`, `rejected`, `canceled`, `discarded`를 구성합니다. 상태 전이와 알림은 제품 서비스를 통해 만들고, 읽은 알림과 읽지 않은 알림을 함께 남깁니다. 팀·지원의 공모전 문맥, 현재 소속, 정원, 사건 이력의 일관성을 검사합니다.

예약 계정도 사람이 시연 중 직접 지원하거나 프로필을 수정할 수 있습니다. 다음 시연 전에는 진단 결과와 현재 프로필을 확인합니다. 일반 시드 재실행은 기존 상태를 보존하므로 이를 초기화 명령으로 사용하지 않습니다.

## 개발 비밀번호 갱신

현재 공개 개발용 비밀번호는 최신 `develop`과 같은 `WejoDev2026!Demo`입니다. [비밀번호 입력 정책](../specs/authentication.md#password-policy)의 길이·기호·한글과 공백 제한을 그대로 검증합니다. 시드의 `DEV_PASSWORD` 상수만 바꾸거나 일반 시드를 재실행해도 기존 계정의 비밀번호는 변경되지 않습니다.

2.1.1 복구 작업에서는 실제 개발 DB에 명령을 실행하지 않았습니다. 과거 2.1.0의 적용 보고서는 [버전 이력](versions.md)에 별도로 기록하며 현재 비밀번호의 적용 증거로 사용하지 않습니다. 명령은 현재 코드가 있는 최신 `develop` 기반 작업 트리의 `backend/`에서 실행합니다.

[개발 비밀번호 갱신 명령](../../backend/scripts/reset_dev_passwords.py)은 로컬 `wejo_dev`의 고정 시드 UUID와 로그인 ID가 일치하는 계정만 대상으로 합니다. 현재 가입 DTO와 실제 차단 목록을 검사한 뒤 새 비밀번호와 다른 해시만 갱신하고, 프로필·팀·지원·알림·기존 세션은 보존합니다. 차단 목록 파일·버전이 없거나 새 비밀번호가 차단되면 실행을 거부합니다.

암호 해시 확인·갱신에는 시간이 걸릴 수 있습니다. 명령은 10개 계정마다 DB 연결을 확인하면서 한 트랜잭션을 유지하므로 실행 중간의 flush를 부분 적용 완료로 해석하지 않습니다.

아래 명령은 `backend/`에서 실행합니다. `--apply`가 없으면 검증 후 전체 롤백하며, 실제 변경 전에는 [백업 절차](#rebuild)를 따릅니다.

```bash
uv run python -m scripts.reset_dev_passwords \
  --blocklist ../data/security/seclists-top-1000000.txt \
  --blocklist-version seclists-xato-1m-c205c36a445b

uv run python -m scripts.reset_dev_passwords \
  --blocklist ../data/security/seclists-top-1000000.txt \
  --blocklist-version seclists-xato-1m-c205c36a445b \
  --apply --report ../data/reports/demo-v2-passwords-applied.json
```

사용한 목록은 [SecLists의 고정 revision 원본](https://raw.githubusercontent.com/danielmiessler/SecLists/c205c36a445bff37f8e58a9ec829105cd4975c58/Passwords/Common-Credentials/xato-net-10-million-passwords-1000000.txt)의 100만 행입니다. 파일과 출처·버전·SHA-256 메타데이터 `data/security/seclists-top-1000000.source.json`은 모두 Git에서 제외합니다. 이 로컬 명령에 제공한 목록은 운영 서버의 차단 목록 설정을 변경하지 않습니다.

## 실행과 재구성

먼저 [로컬 실행](../development/local-development.md)에 따라 개발 DB와 현재 마이그레이션을 준비합니다. 아래 시드 명령은 `backend/`에서 실행합니다.

```bash
# 현재 데이터를 읽고 분포·추천 후보·무결성을 진단합니다.
uv run python -m scripts.seed_dev_data --check \
  --report ../data/reports/demo-v2-check.json

# 없는 계정·팀만 추가합니다. --apply가 없으면 생성·검증 후 전체 롤백합니다.
uv run python -m scripts.seed_dev_data
uv run python -m scripts.seed_dev_data --apply
```

시드 명령의 `--report`를 생략하면 `data/reports/dev-dataset/2.1.1/`에 실행 시각을 이름으로 한 보고서가 생성됩니다. 원하는 경로를 지정할 때도 Git에서 제외된 `data/` 아래를 사용합니다.

기존 팀이 마감 공고에 집중되어 있거나 시연 상태를 다시 만들려면 `--rebuild-teams`를 명시합니다. 이 옵션은 시드 팀과 연결된 가상 지원·소속·사건·알림을 재구성합니다. 해당 팀·지원에 연결된 만료된 가상 계정의 AI 검토 실행 메타데이터도 정리합니다. 기존 계정·프로필·실제 공모전·일반 AI 대화와 메시지는 보존합니다.

시드 팀에 일반 계정의 활동이 연결돼 있거나, 연결된 AI 검토 실행이 아직 만료되지 않았거나 일반 계정 소유이면 재구성을 중단합니다. 재구성할 팀의 기존 가상 지원과 알림은 새 이력으로 바뀌므로 먼저 DB 백업을 남깁니다.

실행 중인 Compose의 PostgreSQL을 사용하는 경우, 저장소 루트에서 다음과 같이 백업합니다. 파일 이름은 실행마다 바꿔 이전 백업을 보존합니다.

```bash
mkdir -p data/backups
docker compose --env-file /dev/null exec -T postgres \
  pg_dump -U wejo -d wejo_dev -Fc \
  > data/backups/wejo_dev-before-demo-v2.dump
docker compose --env-file /dev/null exec -T postgres pg_restore --list \
  < data/backups/wejo_dev-before-demo-v2.dump
```

`--env-file /dev/null`은 이미 실행 중인 Compose 컨테이너에 명령을 전달할 때 루트 `.env` 파싱을 생략합니다. 다른 PostgreSQL 환경이면 해당 로컬 개발 DB에 맞는 `pg_dump`를 사용합니다. 실제 계정의 비밀번호나 DB 접속 비밀값을 명령·문서·보고서에 기록하지 않습니다.

백업 목록을 확인한 뒤 `backend/`에서 예행 실행과 실제 적재를 순서대로 수행합니다.

```bash
uv run python -m scripts.seed_dev_data --rebuild-teams \
  --report ../data/reports/demo-v2-preview.json

uv run python -m scripts.seed_dev_data --rebuild-teams --apply \
  --report ../data/reports/demo-v2-applied.json

uv run python -m scripts.seed_dev_data --check \
  --report ../data/reports/demo-v2-check.json
```

예행 실행의 `rolled_back`은 실제 DB 저장 완료를 뜻하지 않습니다. 적용 후 읽기 진단에서 최종 상태를 확인합니다. `--check`는 품질 오류가 있으면 보고서를 저장한 뒤 종료 코드 1을 반환합니다. `validation.quality.errors`로 원인을 확인하고, 경고는 `validation.quality.warnings`에서 확인합니다. 제작은 한 트랜잭션으로 수행하며 오류가 나면 전체를 롤백합니다. 일반 시드와 재구성은 동시에 실행하지 않습니다.

복원이 필요하면 백업을 먼저 별도 로컬 DB로 복원해 내용과 연결을 확인합니다. 백업 이후의 개발 변경도 함께 사라질 수 있으므로 현재 DB에 바로 덮어쓰지 않습니다. 백업 파일과 전체 보고서는 `data/` 안에 유지하며 Git에 강제 추가하지 않습니다.

## 시연 순서

| 순서 | 화면·계정 | 보여 줄 내용 |
| --- | --- | --- |
| 1 | 공모전 탐색 | 등록순과 마감 정보를 보며 팀이 있는 서로 다른 공모전 2~3개를 선택 |
| 2 | `devuser299`의 팀 탐색·AI | 여러 공모전의 모집 중 팀과 실제 모집 역할을 비교 |
| 3 | 같은 계정의 팀 상세 | 추천 근거와 팀 소개를 확인한 뒤 사용자가 직접 지원 |
| 4 | 해당 팀장 계정 | 새 지원과 기존 지원자를 비교하고 AI 검토·검토 중 전환·선발을 구분 |
| 5 | 지원자 계정·알림 | 상태 변경과 읽음 처리, 선발 후 소속을 확인 |
| 6 | 다른 팀장·`devuser300` | 정원 충족·팀장 종료 상태와 비공개 프로필의 지원 전 공개 전환 흐름 확인 |

처음에는 `devuser002`처럼 각 쌍의 두 번째 팀장을 사용하면 모집 중인 팀의 지원·검토 흐름을 시작하기 쉽습니다. 실제 팀 이름과 공모전은 실행 보고서에서 확인합니다. 특정 제목이나 팀 ID를 발표 자료에 고정하기 전에는 적용된 버전과 기준 시각을 함께 기록합니다.

AI 질문 예시는 현재 데이터에 있는 분야와 모집 역할을 먼저 확인한 뒤 사용합니다.

- “마감까지 여유가 있고 기획 역할로 지원할 수 있는 팀을 찾아줘.”
- “영상이나 디자인 공모전 팀을 비교해줘. 다른 공모전의 팀도 보여줘.”
- “이 팀의 기존 지원자 중 검토할 사람을 실제 프로필 근거로 비교해줘.”

AI 답변과 추천 카드 자체는 미리 만들어 적재하지 않습니다. 데이터 검증은 후보가 존재하고 접근 가능한지를 확인하며, 실제 LLM 답변 품질·지연이나 프론트 연결 성공까지 보장하지 않습니다. AI 응답의 성공 여부는 별도로 시연 환경에서 확인합니다.

## 시연 전 확인과 갱신

`--check` 보고서에서 공모전별 팀 수, 현재 모집 가능한 팀, 예약 계정의 추천 가능한 후보, 지원 상태 분포와 무결성을 확인합니다. 전체 팀 수 외에 **AI가 처음 조회하는 최신 팀 목록에 서로 다른 공모전의 지원 가능한 팀이 남는지**를 확인해야 합니다. 같은 공모전에 이미 소속된 사용자는 해당 공모전의 다른 팀도 신규 추천에서 제외되기 때문입니다.

마감으로 모집 후보가 줄면 재구성 예행 실행부터 다시 수행합니다. 후보가 부족하다는 경고는 실제 공고를 추가·갱신할 신호입니다. 원문이 확인되지 않은 공고를 임의 수정하거나 제품의 접수·정원·공개 조건을 풀어 해결하지 않습니다.

제작 규칙을 변경했다면 코드·테스트·이 문서·[버전 이력](versions.md)을 같은 변경에 포함합니다. 원본 전체 대신 입력 식별용 해시와 작은 검증 집계만 Git에 남깁니다.
