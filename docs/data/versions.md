# 데이터 버전과 변경 이력

데이터셋 버전은 개발·시연 자료를 **어떻게 만드는지**를 식별합니다. DB 스키마 버전이나 실행 시각과 별개입니다. 제작·재구성 명령은 [시연 데이터 운영](demo-dataset.md), 스키마 적용은 [로컬 실행](../development/local-development.md)을 따릅니다.

## 버전과 실행 기록

제작 규칙의 버전은 [분배 계획 코드](../../backend/scripts/dev_dataset.py)의 `DATASET_VERSION`에서 관리하고 이 문서에 변경 이유를 기록합니다.

| 변경 | 버전 규칙 |
| --- | --- |
| 기존 시연 상태·ID 사용법·입력 계약과 호환되지 않는 재구성 | 주 버전 증가 |
| 기존 사용법을 유지하면서 분야·규모·시나리오 추가 | 부 버전 증가 |
| 같은 의도·구조 안의 데이터 제작 오류 수정 | 수정 버전 증가 |
| 설명·링크만 수정하고 제작 결과는 동일 | 데이터 버전 유지 |

같은 버전의 재실행도 기준 시각과 공고 집합이 달라지면 다른 실행 결과입니다. 실행 보고서의 주요 식별 필드는 다음과 같습니다.

| 필드 | 의미 |
| --- | --- |
| `datasetVersion` | 이번 명령을 실행한 제작 규칙의 버전 |
| `schemaRevision` | 실행 대상 개발 DB의 Alembic revision |
| `referenceAt` | 공모전 선정·분포 진단의 UTC 기준 시각 |
| `generatorSha256` | 제작 코드·고정 ID 목록·학사 입력 문서의 식별 해시 |
| `catalogSha256` | 기존 DB 공고 전체 컬럼·분야·참가 대상의 식별 해시 |
| `status` | `applied`: 실제 적재, `rolled_back`: 예행 실행, `checked`: 읽기 진단 |
| `validation` | 현재 팀 분포·지원 상태·예약 계정·추천 후보·품질 진단 |

`datasetVersion`은 DB에 저장된 적용 버전 표식이 아닙니다. 이전 데이터에 `--check`를 실행해도 현재 제작 규칙 버전이 출력됩니다. 실제 적용은 해당 실행의 `status=applied` 보고서와 후속 진단으로 확인합니다. 원본 파일을 새로 반입했다면 그 원본의 SHA-256과 출처도 로컬 기록에 보관합니다. `catalogSha256`과 원본 파일 바이트 해시는 서로 다른 대상을 식별합니다.

동일한 코드·입력·기준 시각은 선정·배정 계획을 재현하는 조건입니다. 비밀번호 해시의 salt, 서비스가 생성하는 지원·사건 ID와 실행 시각까지 동일한 DB 바이트를 보장하지 않습니다. 이미 사용 중인 개발 DB는 사람의 편집 상태도 결과에 영향을 줍니다. 완전히 같은 실행 상태가 필요하면 해당 실행의 로컬 DB 백업을 사용합니다.

Git에는 코드와 아래 집계처럼 작은 메타데이터만 보관합니다. `data/`의 원본·가공본·개인별 레코드·전체 보고서·DB 덤프는 추적하지 않습니다. 특정 실행을 팀에 전달할 때는 코드 버전과 로컬 산출물의 체크섬을 함께 전달합니다.

## 2.1.1 — 최신 develop으로 미반영 제작 도구 복구

로컬 작업에 남아 있던 분산 계획·진단·재구성·개발 비밀번호 갱신 도구를 최신 `develop` 코드와 맞춥니다. 기존 `--refresh-content`, 사용자 편집 보존, 과목 필드가 추가되기 전 원문 비교, 테스트 DB 격리를 유지합니다. 현재 AI의 구조화 `roleCode` 검색과 보고서의 역할별 후보가 같은지 검사합니다.

개발용 비밀번호는 `develop`의 `WejoDev2026!Demo`를 유지합니다. 과거 작업 파일에 남은 다른 값으로 바꾸지 않으며, 신규 생성·명시적 갱신 모두 현재 가입 DTO로 길이와 문자 조건을 검사합니다. 갱신 도구는 실제 차단 목록 확인·고정 ID 대조·전체 롤백·기존 세션 보존 조건을 유지합니다.

이번 작업은 코드와 격리 테스트 DB의 회귀 검증이며 실제 `wejo_dev` 재구성이나 비밀번호 갱신을 수행하지 않습니다. 적용 상태는 이후 실행의 보고서로 확인합니다.

## 2.1.0 — 과거 로컬 개발 비밀번호 갱신 기록

기존 로컬 산출물 `data/reports/demo_v2_1_password_applied.json`에는 2026-10-31 19:11 KST(`2026-10-31T10:11:00.983585Z`)에 300개 계정 검사·300개 갱신·누락 0개, `status=applied`가 기록되어 있습니다. `demo_v2_1_password_idempotent.json`에는 19:12 KST 재실행에서 300개 검사·추가 갱신 0개가 기록되어 있습니다.

이 기록은 당시 작업의 결과입니다. 보고서에는 비밀번호 원문을 저장하지 않으므로 현재 코드의 비밀번호가 해당 계정에 적용되어 있다고 판단하지 않습니다. 과거 문서의 비밀번호 길이 설명과 복구된 상수 값은 일치하지 않아 현재 실행 안내에서 제외했습니다. 현재 정책·명령과 검증 범위는 2.1.1과 [개발 비밀번호 갱신](demo-dataset.md#dev-passwords)을 따릅니다. 원본 보고서와 관련 인증 검증 산출물은 Git에서 제외한 `data/reports/`에 유지합니다.

## 2.0.0 — 공모전 분산과 시연 후보 유지

**과거 `main` 기반 작업 트리에서 로컬 `wejo_dev` 적용 완료: 2026-10-31 18:33:51 KST.** 기준 시각은 `2026-10-31T09:33:51Z`, DB revision은 `20261031_10`입니다. 아래 수치는 당시 실행의 역사 기록이며, 현재 `develop` 코드의 검증을 마쳤거나 운영에 배포했다는 뜻은 아닙니다. 이후에도 같은 모집 상태가 유지된다는 보장은 없습니다.

기존 100개 팀이 두 공모전에 50개씩 집중됐고 두 공모전이 모두 마감되어 신규 지원·추천 후보가 없어진 문제를 해결합니다. 기존 공고와 가상 사용자·프로필을 재사용하고 시드 팀 관계만 명시적 옵션으로 재구성합니다.

- 현재 접수 중·확인된 팀 인원·최소 7일 마감 여유를 필수 조건으로 사용합니다.
- 분야 다양성, 최신 등록, 마감 여유를 함께 고려해 최대 25개 공모전에 배정합니다.
- 100개 팀을 목표로 하되 공모전당 6개 상한을 지키며, 후보가 부족하면 팀 수를 줄입니다.
- 공모전별 모집 중 팀과 상태 시연용 팀을 함께 두고 최신순에서도 공모전을 섞습니다.
- 두 예약 계정을 자동 지원·선발에서 제외해 신규 추천·지원 시연의 시작점을 마련합니다.
- 재구성 범위의 만료된 가상 계정 AI 검토 메타데이터를 정리하며, 미만료 실행·일반 계정 활동은 중단 조건으로 보호합니다.
- 원본을 Git에 넣지 않고 제작 코드·문서·버전과 로컬 실행 보고서를 분리합니다.

| 항목 | 2026-10-31 재구성 전 조사 | 2.0.0 실제 적용 |
| --- | --- | --- |
| 실제 공모전 | 490개 | 490개 보존, 공고 해시 일치 |
| 가상 계정·학사 항목 | 계정 300개·학사 94개 | 기존 값 보존 |
| 프로필 공개 상태 | 공개 240개·비공개 60개 | 기존 값 보존 |
| 가상 팀 | 100개 | 100개 재구성 |
| 팀이 연결된 공모전 | 2개, 모두 마감 | 22개, 모두 접수 중 |
| 공모전당 가상 팀 | 각 50개 | 4~6개 |
| 현재 모집 가능한 팀 | 0개 | 75개 |
| 모집 종료 팀 | 기존 상태 유지 | 25개: 정원 충족 13개·팀장 종료 12개 |
| 지원·상태 사건·알림 | 이전 공모전에 연결된 이력 | 지원 1,200개·사건 2,045개·알림 3,245개 |

선정 공모전 22개는 분야가 있는 18개와 미분류 4개를 포함합니다. 초기 분야 연결 조회에서 빠진 4개도 접수·인원 조건을 확인해 포함했으며, 분야를 새로 추정해 넣지는 않았습니다. 모집 중인 팀은 창업·디자인·교육·보건·IT·영상·정책의 7개 등록 분야와 6개 모집 역할을 제공합니다.

지원 상태는 `submitted` 398개, `reviewing` 170개, `selected` 100개, `rejected` 200개, `canceled` 213개, `discarded` 119개입니다. 알림은 읽음 1,100개·미읽음 2,145개입니다. `devuser299`·`devuser300`은 지원과 현재 소속이 모두 0개이며 기본 공개·비공개 상태를 유지했습니다.

추천 후보 검증에서 최신 8개 팀은 서로 다른 공모전 5개에 걸쳐 있었고, `devuser001`·`devuser101`·`devuser299`·`devuser300` 모두 8개를 추천받을 수 있었습니다. `devuser299`의 역할별 첫 페이지도 6개 역할 모두 후보 8개를 확보했습니다. 이는 제품 조회·추천 허용 조건을 검증한 결과이며 실제 LLM 응답은 호출하지 않았습니다.

공통 표시를 `[시연용 가상팀]`으로 바꾸어 `개발용` 문구가 비개발 팀을 개발 검색에 포함시키던 문제를 제거했습니다. 실제 AI의 키워드 검색 첫 페이지에서도 역할 일치 후보가 6~8개이며, `개발` 검색 결과 8개는 모두 개발 역할을 모집합니다. 별도 ASGI 검증 설정으로 실제 개발 DB의 세 계정 로그인·본인 조회·로그아웃과 팀 상세 100개를 확인했고, `SourceReader`의 실제 검색·현재 권한 검증도 통과했습니다. 브라우저의 실제 인증 설정이나 LLM 제공자는 이 검사에 사용하지 않았습니다.

적용 시점의 가장 이른 모집 마감은 **2026-11-09 00:00 KST**로 약 8.23일 남았습니다. 선정 계획에는 목표 25개보다 적은 22개를 사용한다는 안내와, 16개 공고가 21일 미만 남았다는 안내가 있습니다. 현재 데이터의 품질 진단은 오류 0개·경고 0개로 통과했으며, 날짜가 지나면 다시 확인해야 합니다.

단위 테스트 23개와 실제 PostgreSQL 통합 테스트 6개, 총 29개가 통과했습니다. 변경 범위의 Ruff·타입 검사도 통과했습니다. 프론트 화면 시연과 실제 LLM 답변 품질 검증은 이 결과에 포함하지 않습니다.

로컬 최종 적용 보고서는 `data/reports/demo_v2_final_applied.json`, API 검증은 `data/reports/demo_v2_api_verification.json`에 보관합니다. 재구성 전 백업을 유지하며, 공모전의 전체 컬럼·분야·참가 대상 해시는 적용 전후 동일합니다. 계정·학사·프로필·관심 분야·희망 역할·역량·포트폴리오·기존 AI 대화와 메시지도 전체 행 해시가 동일함을 확인했습니다. 이 실행의 작은 식별 정보는 다음과 같습니다.

## 이전 시드 — 2026-10-26

명시적인 데이터셋 버전 필드가 없던 기존 시드를 비교 기준으로 기록합니다. 가상 사용자 300개, 팀 100개, 지원 1,200개를 생성하고 선발·취소·미선발·폐기·알림 상태를 구성했습니다. 최초 두 공모전에 팀이 연결됐으며, 이후 실제 공모전이 490개로 늘어도 기존 팀을 건너뛰는 방식 때문에 분포가 갱신되지 않았습니다.

기존 기본 시드의 “있는 계정·팀은 보존” 동작은 2.0.0에서도 일반 실행에 유지합니다. 기존 팀을 분산하려면 `--rebuild-teams`가 필요합니다. 과거 결과는 로컬 `data/reports/dev_seed_2026-10-26.json`과 재구성 전 백업으로 보관합니다.
