# 문서 리뷰와 게시 확인하기

PR 리뷰는 문장이 읽기 좋은지뿐 아니라 **이 내용대로 만들어도 되는지** 확인하는 과정입니다. 문서 작성·PR 생성은 [웹 수정 안내](editing-docs.md), 정책과 완료 조건의 기준은 [명세 작성 안내](writing-specs.md)를 참고합니다.

## 리뷰를 요청받았다면

1. PR의 **Conversation**에서 변경 이유, 범위, 작성자가 묻는 내용과 문서 기준 `develop` 커밋을 읽습니다. 최신 `develop`의 관련 문서가 이후 바뀌었다면 함께 비교합니다.
2. **Files changed**에서 바뀐 부분을 확인합니다. `-` 표시는 삭제, `+` 표시는 추가입니다. 바뀐 줄만으로 맥락이 부족하면 파일 메뉴의 **View file**로 해당 브랜치의 전체 문서를 읽습니다.
3. 기획 관점에서 목적·사용자 흐름·정책·예외·완료 조건이 서로 맞는지 확인합니다. “실패하면 사용자는 무엇을 보나요?”, “이번 범위에 알림도 포함되나요?”처럼 판단할 수 있는 질문을 남깁니다.
4. 특정 문장은 줄 옆 댓글 버튼으로 의견을 남깁니다. **Start a review**로 시작한 댓글은 아직 본인에게만 보이므로 마지막에 리뷰를 제출해야 합니다.
5. **Review changes**에서 결과를 고르고 **Submit review**를 누릅니다.

| 리뷰 선택 | 언제 사용하나요? |
| --- | --- |
| Comment | 질문이나 참고 의견을 남길 때. 승인으로 계산되지 않음 |
| Approve | 내 검토 범위에서 내용에 동의하고 반영해도 된다고 판단할 때 |
| Request changes | 반영 전에 반드시 고쳐야 할 정책·누락·오류가 있을 때. 이유와 필요한 변경을 함께 적음 |

본인이 작성한 PR에는 스스로 승인할 수 없습니다. 기획 리뷰에서 기술 구현까지 검증한 것처럼 적을 필요는 없습니다. 예를 들어 “사용자 흐름과 마감 정책을 검토했고 이 내용에 동의합니다”처럼 확인한 범위를 밝힙니다.

## 수정 요청을 받았다면

1. 요청의 의미가 불명확하면 해당 댓글에서 먼저 확인합니다. 결정이 바뀌었다면 이유를 답변합니다.
2. **기존 PR의 작업 브랜치**에서 문서를 수정하고 커밋합니다. 여러 수정도 같은 PR에 쌓입니다.
3. 댓글에 어디를 어떻게 고쳤는지 답하고, 논의가 해결되었는지 확인합니다. **Resolve conversation**은 해당 대화를 해결 상태로 표시하는 기능입니다.
4. 변경을 요청한 리뷰어에게 PR의 **Reviewers**에서 재검토를 요청합니다. 버튼이 보이지 않으면 댓글로 재검토를 요청합니다.

**수정 커밋이나 대화 해결만으로 `Request changes`가 해소되지는 않습니다.** 변경을 요청했던 리뷰어의 재검토·승인이 필요합니다. 새 변경이 올라오면 이전 승인이 해제될 수 있으므로 마지막 수정 후 리뷰 상태를 다시 확인합니다.

리더 예외와 리뷰 기각 등 예외 처리는 [팀 작업 흐름](../development/workflow.md)의 기준을 따릅니다. 일반 팀원이 다른 승인 하나를 받아 변경 요청을 건너뛰는 방식으로 처리하지 않습니다.

## 검사 결과와 병합 확인하기

PR에는 **Checks** 또는 하단 검사 목록이 표시됩니다. 자동 검사를 CI라고 부릅니다.

| 검사 이름 | 확인하는 것 |
| --- | --- |
| Validate docs | 원본 문서 링크, 문서 사이트 빌드, 생성된 HTML의 링크·앵커·자산 |
| PR conventions | PR 제목 형식과 작업 PR이 `develop`을 대상으로 하는지 |
| Frontend · Backend | 변경 영향에 필요한 앱·브라우저 검사 결과와 명시적 생략 여부 |

문서만 바꾼 PR에도 `Frontend`·`Backend` 필수 검사 이름은 표시되지만, 앱 영향이 없으면 실제 앱·브라우저 검사는 생략합니다. `develop`과 `main` 병합 후에는 전체를 검사합니다. [검사 범위](../development/testing.md#ci-scope)에 따라 자동 결과를 확인하고, 실패했다면 오류가 난 검사 링크를 개발자에게 전달합니다. 기획 팀원이 로컬 개발 환경을 설치해 모두 실행할 필요는 없습니다. **초록 체크는 정책과 사용자 경험에 대한 사람의 승인을 대신하지 않습니다.**

일반 팀원의 문서 작업 PR 병합에는 작성자 외 승인, 변경 요청 해소, 필수 검사 성공, 최신 `develop` 반영, 리뷰 대화 해결이 필요합니다. 버튼이 활성화되었다고 내용 합의까지 끝났다는 뜻은 아닙니다. 중요한 미정 사항과 리뷰를 확인한 뒤 **Squash and merge**로 `develop`에 반영합니다. 처음 병합할 때는 리더와 함께 진행해도 됩니다. 릴리스·동기화 PR의 Merge commit 예외와 정확한 필수 검사·리더 예외는 [팀 작업 흐름](../development/workflow.md)에서 관리합니다.

`Squash and merge`를 누른 뒤 병합 제목·설명을 확인하고 최종 확인 버튼까지 눌러 **Merged** 상태를 확인합니다. PR 제목과 설명은 병합 기록의 기본값이므로 실제 합의·변경 결과에 맞게 정리합니다.

**Approve**는 리뷰 결과, **Merged**는 실제 반영 완료입니다. `Closed`만 표시되고 `Merged`가 없다면 변경이 반영되지 않은 상태입니다.

## 사이트에서 확인하기

1. 작업 PR이 `develop`에 **Merged**인지 확인합니다. 개발·후속 작업은 릴리스 여부와 관계없이 [develop의 문서](https://github.com/wejo-team/sku-dreamon/blob/develop/docs/README.md)를 기준으로 합니다. 열려 있는 PR의 내용은 GitHub의 변경 파일에서 확인하며, 별도 PR 미리보기 사이트는 없습니다.
2. 해당 변경을 포함한 `develop` → `main` 릴리스가 병합된 뒤 [Actions의 Docs and Pages](https://github.com/wejo-team/sku-dreamon/actions/workflows/docs.yml)에서 그 `main` 실행을 확인합니다. **Publish Pages**가 성공하면 사이트가 갱신됩니다.
3. [문서 사이트](https://wejo-team.github.io/sku-dreamon/)에서 문서를 다시 열어 내용과 링크를 확인합니다. 바로 안 보이면 게시 완료를 기다린 뒤 새로고침하고, 페이지의 원본 커밋 링크로 버전을 확인합니다.

사이트는 `main`의 `docs/` 원본을 자동 게시한 릴리스 스냅샷입니다. 수정은 최신 `develop`에서 시작하는 문서 PR로 진행합니다.

## 막혔을 때

| 보이는 상황 | 다음 행동 |
| --- | --- |
| 편집·브랜치 생성이 안 되거나 Fork를 요구함 | 로그인 계정과 조직 초대 수락을 확인하고 리더에게 저장소 Write 권한 확인 요청 |
| PR에 변경 파일이 없거나 엉뚱한 변경이 보임 | base가 `develop`, compare가 내 브랜치인지 확인. 파일이 해당 브랜치에 커밋되었는지 확인 |
| PR conventions가 빨간색 | 제목이 `docs: 변경 내용`, base가 `develop`, compare가 `docs/…` 작업 브랜치인지 확인한 뒤 새 검사 결과 확인 |
| 다른 검사가 실패함 | 실패한 검사와 PR 링크, 바꾼 파일을 개발자에게 전달. 검사 설정을 끄거나 보호 규칙을 변경하지 않음 |
| 충돌(conflict) 또는 브랜치 업데이트 필요 | 같은 부분의 변경을 함께 확인할 수 있도록 개발자에게 PR 링크 전달. 타인의 변경을 통째로 덮어쓰지 않음 |
| 리뷰를 했는데 승인이 부족함 | 댓글만 남긴 것은 아닌지, Submit review를 눌렀는지, 수정 후 재승인이 필요한지 확인 |
| 병합했는데 게시 내용이 예전 그대로임 | 변경이 main 릴리스에 포함되었는지 먼저 확인하고 해당 main의 게시 실행·원본 커밋 확인. 실패했으면 실행 링크와 함께 담당자에게 요청 |

도움을 요청할 때는 **PR 주소 + 하려던 일 + 화면의 오류 문구 또는 검사 링크**를 함께 전달하면 빠르게 확인할 수 있습니다.
