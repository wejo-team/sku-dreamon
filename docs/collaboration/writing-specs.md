# 기능 명세 작성하기

명세는 **누가, 어떤 상황에서, 무엇을 하면, 어떤 결과가 생겨야 하는지** 팀이 합의하는 문서입니다. 기획자는 사용자 경험과 정책을 설명하고, 개발자는 이를 바탕으로 구현 방법을 계획합니다.

파일을 만드는 방법은 [GitHub 웹 수정 안내](editing-docs.md)를 따릅니다. 작성 양식은 [기능 명세 템플릿](../templates/spec.md), 실제 명세 목록은 [명세 인덱스](../specs/README.md)에 있습니다.

## 어떤 문서를 수정하나요?

| 상황 | 작성 방법 |
| --- | --- |
| 기존 기능의 정책을 변경 | 기존 명세를 수정하고 PR에 변경 이유와 영향을 설명 |
| 새 기능을 제안 | 템플릿을 `docs/specs/<기능-이름>.md`에 복사하고 인덱스에 연결 |
| 아직 문제·방향부터 논의해야 함 | [Issue](https://github.com/wejo-team/sku-dreamon/issues)에 배경과 질문을 남기고, 방향이 정리되면 명세 PR로 연결 |
| 표현·오탈자만 정리 | 해당 문서를 수정하는 작은 PR. 별도 기능 명세는 필요 없음 |

같은 기능의 최종본·수정본을 여러 파일로 만들지 않습니다. 변경 이력은 GitHub에 남고, 검토 중인 내용은 PR에서 구분합니다.

## 양식에 무엇을 적나요?

| 항목 | 답해야 할 질문 |
| --- | --- |
| 목적과 사용자 | 어떤 사용자의 어떤 문제를 해결하는가? |
| 범위 | 이번에 제공할 동작은 무엇이며, 이번에 하지 않을 것은 무엇인가? |
| 사용자 흐름과 동작 | 시작 조건 → 사용자 행동 → 화면이나 상태의 결과는 무엇인가? |
| 정책과 예외 | 누가 할 수 있는가? 정보 누락·중복·마감·실패 때 어떻게 되는가? |
| 완료 조건 | 무엇을 관찰하면 요구한 대로 만들어졌다고 확인할 수 있는가? |
| 미정 사항 | 누구와 어떤 결정을 더 해야 하는가? 결정 전 무엇이 영향을 받는가? |

각 항목은 필요한 만큼만 작성합니다. API 경로, DB 테이블, 라이브러리 선택은 이후 개발 계획에서 다룹니다. 화면 설계가 있다면 링크를 함께 두되, 동작과 정책은 명세 본문만 읽어도 이해할 수 있게 씁니다.

## 확인 가능한 문장으로 쓰기

아래는 작성 방법을 보여 주는 **가상의 모집 기능 예시**이며, 서경드림온의 확정 정책이 아닙니다.

| 모호한 문장 | 확인할 수 있는 문장 예시 |
| --- | --- |
| 편리하게 모집글을 작성한다. | 필수 항목을 입력하고 등록하면 작성한 모집글의 상세 화면을 보여 준다. |
| 입력을 잘못하면 오류를 표시한다. | 제목이 비어 있으면 등록하지 않고 제목 입력란에 안내를 표시한다. 다른 입력값은 유지한다. |
| 마감된 모집글은 적절히 처리한다. | 마감된 모집글의 상세 내용은 볼 수 있지만 신청할 수 없고, 마감 상태를 표시한다. |

“적절히”, “잘”, “빠르게”만으로 끝내지 말고 결과를 적습니다. 수치나 정책을 아직 결정하지 못했다면 임의로 확정하지 않고 미정 사항으로 남깁니다.

완료 조건은 하나씩 검증할 수 있게 쓰고 번호를 붙입니다.

```markdown
- [ ] AC-01: 필수 항목을 입력하고 등록하면 작성한 모집글의 상세 화면이 열린다.
- [ ] AC-02: 제목이 비어 있으면 등록되지 않고 제목 입력란에 안내가 표시된다.
```

번호는 개발 계획·검증 결과를 연결하는 기준입니다. 새 조건에는 새 번호를 붙이고, 이미 참조된 번호를 다른 의미로 재사용하지 않습니다. 명세 PR에서는 체크하지 않습니다.

## 검토 요청 전 확인하기

- 정상 동작뿐 아니라 권한·정보 누락·실패 등 이번 기능에 필요한 예외가 있는가?
- 범위 밖 항목과 미정 사항이 드러나 있는가? 중요한 정책 결정을 개발자에게 숨은 숙제로 넘기고 있지 않은가?
- 기존 명세와 충돌한다면 어느 정책을 왜 바꾸는지 설명했는가?
- 새 문서라면 명세 인덱스에 연결했는가? 예시·화면 링크에 실제 개인정보가 들어 있지 않은가?

미정 사항이 있어도 초안을 공유할 수 있습니다. PR에 **무엇을 결정해 달라는지** 적고, 중요한 미정 사항은 명세를 확정·병합하기 전에 해결합니다. 회의나 채팅에서 결정했다면 PR에 이유를 남기고 명세 본문에도 반영합니다. AI로 초안을 만들었어도 서비스 정책과 완료 조건은 사람이 검토합니다.

## 합의 이후의 상태

새 명세는 `구현 상태: 예정`으로 시작합니다. `명세 검토`에는 명세 PR을, `구현 작업`에는 이후 생성되는 Issue 또는 구현 PR을 연결합니다.

명세가 승인·병합되어도 구현 상태와 완료 조건 체크를 바꾸지 않습니다. 개발자는 명세를 기준으로 계획을 세우고 구현하며, 구현 PR에서 실제 진행·검증 근거에 맞춰 상태를 갱신합니다. `완료`는 코드 병합과 검증을 뜻하며 서비스 운영 배포와는 별개입니다.

기획자는 구현 결과 리뷰에서 `AC-01` 같은 조건별로 화면·동작을 확인합니다. 미리보기 환경이 없거나 확인하지 못한 항목은 미확인으로 남기고 담당자에게 확인 방법을 요청합니다. 새 요구사항이 생기면 명세 변경으로 다시 검토합니다. 자세한 절차는 [팀 작업 흐름](../development/workflow.md)을 참고합니다.
