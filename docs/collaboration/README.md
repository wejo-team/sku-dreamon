# 문서 협업 시작하기

GitHub를 처음 사용하는 팀원을 위한 문서 협업 안내입니다. 기획 팀원의 명세 작성·검토를 중심으로 설명하며, **브라우저만으로 문서를 작성하고 검토를 요청할 수 있습니다.** Git 설치나 개발 환경 설정은 필요하지 않습니다.

이 폴더는 문서를 작성·수정·검토하고 게시 결과를 확인하는 **작업 방법**을 안내합니다. 실제 기능·정책은 [specs/](../specs/README.md), 복사할 양식은 [templates/](../templates/README.md), 팀 공통 절차·병합 기준은 [팀 작업 흐름](../development/workflow.md)에서 관리합니다.

개발 계획은 연결된 구현 PR·Issue에 두고, 별도 문서가 필요할 만큼 길어질 때만 `docs/development-plans/`를 만듭니다. 사이트 자동 게시의 설정과 운영은 [문서 관리와 게시](../development/documentation.md)를 참고합니다.

## 지금 할 일 고르기

| 하고 싶은 일 | 시작할 곳 |
| --- | --- |
| 개발 기준 문서 읽기 | [develop의 문서 인덱스](https://github.com/wejo-team/sku-dreamon/blob/develop/docs/README.md)에서 필요한 문서 선택 |
| 릴리스된 문서 확인 | [문서 사이트](https://wejo-team.github.io/sku-dreamon/)에서 검색하거나 폴더 메뉴 선택 |
| 기존 문서 수정, 새 문서 추가, PR 만들기 | [GitHub 웹에서 문서 수정하기](editing-docs.md) |
| 기능의 동작과 정책 정리하기 | [기능 명세 작성하기](writing-specs.md) |
| 다른 사람의 문서 검토, 수정 요청에 답하기 | [문서 리뷰와 게시 확인하기](review-and-publish-docs.md) |
| 기획의 숨은 전제·미정 정책을 이슈로 논의하기 | [기획 결정 이슈 작성하기](../templates/planning-decision.md) |

처음 작성한다면 아래 준비를 마친 뒤 **웹 수정 안내**를 따라갑니다. 리뷰만 맡았다면 **리뷰 안내**부터 읽으면 됩니다.

## 처음 한 번 준비하기

1. 초대받은 GitHub 계정으로 로그인하고 `wejo-team` 조직 초대를 수락합니다.
2. [팀 저장소](https://github.com/wejo-team/sku-dreamon)를 엽니다. 현재 팀원은 조직 Member, `developers` 팀을 통한 저장소 Write 권한으로 참여합니다. 팀 이름과 관계없이 기획 팀원도 문서 작성에 같은 권한을 사용합니다.
3. 수정할 문서와 관련된 [열린 PR](https://github.com/wejo-team/sku-dreamon/pulls)이 있는지 확인합니다. 같은 문서를 함께 고친다면 먼저 담당 범위를 맞춥니다.

저장소는 공개되어 있어 초대 수락 전에도 읽을 수 있습니다. **읽을 수 있는 것과 수정 권한이 있는 것은 다릅니다.** 브랜치를 만들 수 없거나 개인 저장소로 복사하는 Fork 화면이 나오면 리더에게 계정과 권한을 확인해 달라고 요청합니다.

## 어디에서 무엇을 하나요?

| 장소 | 용도 |
| --- | --- |
| 저장소의 `develop`과 `docs/` | 개발·검토에 사용할 최신 기준 문서 확인·작업 브랜치에서 수정 |
| 문서 사이트 | `main`에서 게시된 릴리스 시점의 문서 확인 |
| Pull requests(PR) | 변경 전후 비교, 질문, 승인, 반영 기록 확인 |
| Issues | 아직 문서 변경으로 정리하기 어려운 질문·제안·작업 논의 |

개발과 문서 작업은 `develop`의 문서를 기준으로 합니다. 사이트에는 아직 릴리스되지 않은 변경이 없을 수 있으므로, 작업을 시작하거나 이어받을 때 [develop의 문서 인덱스](https://github.com/wejo-team/sku-dreamon/blob/develop/docs/README.md)에서 관련 내용을 확인합니다.

우리 팀은 **명세 작성 → 사람 검토·합의 → 개발 계획 → 구현·검증 → 결과 리뷰** 순서로 진행합니다. 새 기능의 명세 PR에는 동작과 정책을 담고, 구현은 이후 별도 작업으로 진행합니다. 세부 기준은 [팀 작업 흐름](../development/workflow.md)을 따릅니다.

## 이 단어만 알면 시작할 수 있어요

| 화면의 단어 | 이 작업에서의 의미 |
| --- | --- |
| Repository · 저장소 | 문서와 코드를 함께 보관하는 팀 공간 |
| `develop` | 새 작업을 시작하고 문서·기능 PR을 반영하는 기본 브랜치 |
| `main` | 릴리스된 코드와 사이트에 게시할 문서의 기준 브랜치 |
| Branch · 브랜치 | `develop`에 반영하기 전에 수정하는 작업 공간 |
| Commit · 커밋 | 변경 이유와 함께 남기는 저장 기록 |
| Pull request · PR | 내 브랜치의 변경을 검토하고 `develop`에 반영해 달라는 요청 |
| Merge · 병합 | 검토한 변경을 PR의 대상 브랜치에 반영하는 작업 |

브랜치에 저장하거나 `develop`에 병합하는 것만으로 사이트가 바뀌지는 않습니다. 변경이 `develop` → `main` 릴리스에 포함되고 자동 게시가 성공해야 사이트에 반영됩니다. 또한 **명세가 게시되었다고 기능이 구현되거나 서비스에 배포된 것은 아닙니다.**

공개 저장소이므로 작업 브랜치와 Draft PR도 공개됩니다. 고객 실명·연락처·비밀번호 같은 실제 정보는 넣지 말고 가상의 예시를 사용합니다.
