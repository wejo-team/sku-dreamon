프로필의 이름·공개 범위를 변경할 때만 [프로필 정책](profile.md)을 함께 읽습니다.

## 목적과 사용자

교내 공모전 참여를 원하는 사용자가 서비스 계정을 만들고 로그인한 뒤 프로필 설정과 참여 흐름을 시작할 수 있게 합니다. 스프린트 1에서는 교내 구성원 여부를 검증하지 않으므로 로그인만으로 교내 사용자임을 보장하지 않습니다.

| 소셜 로그인·계정 연결 | 이번 범위에서 제외; 기존 사용자 계정에 나중에 연결할 수 있도록 계정 식별 원칙만 정의 |
| 계정 복구 | MVP에서 제외; 아이디 찾기·비밀번호 재설정·수동 본인확인 복구 경로를 제공하지 않음 |
| 시연 | 같은 자체 로그인 사용; 별도 인증 우회·가짜 인증 성공 경로를 제공하지 않음 |
| 별도 본인확인 | 신분증 등을 통한 실명 진위 확인은 제외 |

가입 후 필수 프로필 작성은 [프로필 입력 항목](profile.md#fields)에서 정의합니다. 아이디·비밀번호 입력과 [서버 세션·만료·동시 로그인·기본 로그인 유지](#session-policy)는 아래 확정 규칙을 적용합니다. 가입 직후에는 자동 로그인하여 프로필 설정으로 이동합니다. [계정 복구](#account-recovery)는 MVP에서 제외하고, 남은 구현 상세는 미정 사항과 개발 계획에서 다룹니다.

## AUTH-01 결정과 적용 환경

스프린트 1을 실행하는 개발·시연·배포 환경의 사용자 가입 경로는 자체 아이디·비밀번호 방식으로 통일합니다. 배포 여부나 공개 모집 범위를 이 결정으로 확정하지는 않습니다.

| 결정 | 이유와 영향 |
| --- | --- |
| 자체 로그인으로 핵심 흐름 검증 | 학교 메일 발송·학교 계정 정책·소셜 제공자 연동을 이번 개발의 선행 조건에서 제외 |
| 학교 인증은 후속 검토 | 교내 구성원만 가입할 수 있다고 안내할 수 없으며, 로그인 성공으로 교내 인증 완료 표시를 부여하지 않음 |
| 메일 발송을 요구하지 않는 가입 | 인증 메일 발송 비용·설정이 이번 가입 흐름에 필요하지 않음. 서버·DB 운영과 계정 보안·복구 부담은 별도 |
| 내부 사용자 ID 유지 | 나중에 로그인 수단을 추가해도 기존 프로필·소속 팀·지원 내역의 소유자를 유지 |

기존 원문의 ‘실제 학교 이메일 인증 또는 시연 인증’ 선택은 이 결정으로 대체합니다. 실제 계정의 비밀번호를 확인하는 로그인은 구현 대상이며, 학교 인증을 생략하는 것을 로그인 보안 생략으로 취급하지 않습니다.

## 사용자 흐름과 동작

1. 사용자가 회원가입 화면에서 로그인 아이디와 비밀번호를 등록합니다. 이메일·구글 계정은 요구하지 않습니다.
2. 가입 성공 시 자동 로그인하고 프로필 설정으로 이동하여 필수 정보를 작성합니다. 방금 등록한 아이디·비밀번호를 다시 입력하게 하지 않습니다.
3. 내 프로필에서 로그인 상태와 별도로 `교내 미인증` 배지를 확인합니다. 배지를 누르면 학교 인증을 아직 제공하지 않으며 모든 계정이 미인증임을 설명하는 팝업을 엽니다. 같은 안내 문장을 프로필에 상시 반복하지 않습니다.
4. 로그아웃하면 현재 로그인 세션이 서버에서 즉시 회수됩니다. 다른 로그인 세션에는 영향을 주지 않으며, 다시 로그인하면 같은 프로필·팀·지원 내역으로 이어집니다.

공개 공고·팀 모집 정보는 로그인 전에도 탐색할 수 있습니다. 프로필 작성·팀 생성·지원에는 아래 [접근 정책](#access-policy)을 적용하며, 모든 지원 직전에 [필수 프로필 입력](profile.md#before-application)을 확인합니다.

## 정책과 예외

<a id="access-policy"></a>

### 로그인 상태와 접근 권한

[이슈 #40](https://github.com/wejo-team/sku-dreamon/issues/40#issuecomment-6233083623)의 결정은 **공개 공고·팀 모집 정보는 비로그인 탐색을 허용하고, 프로필 작성·팀 생성·지원은 로그인을 요구**하는 것입니다. 로그인한 사용자가 교내 미인증이라는 이유만으로 참여를 막지 않습니다. 로그인 여부와 학교 인증 여부는 서로 다른 기준입니다.

| 화면·행동 | 비로그인 사용자 | 로그인한 교내 미인증 사용자 |
| --- | --- | --- |
| 공개 공고 목록·상세 탐색 | 허용 | 허용 |
| 공개 팀 모집 목록·상세 탐색 | 허용 | 허용 |
| 본인 프로필 작성·수정 | 로그인 필요 | 허용; 필수 항목·공개 설정은 프로필 정책 적용 |
| 팀 생성 | 로그인 필요 | 팀 생성 조건을 충족하면 허용; 교내 미인증만으로 차단하지 않음 |
| 지원 제출 | 로그인 필요 | 공개 프로필에서만 신규 제출. 모든 지원 직전에 필수 프로필·공개 상태·현재 지원 조건 확인; 교내 미인증만으로 차단하지 않음 |
| 다른 사용자의 목록·상세 프로필 | 로그인 필요. 공개 모집 정보 탐색 허용에 포함하지 않음 | [전체 프로필 공개 상태](profile.md#people-directory) 적용. 공개 프로필은 등록된 모든 항목 열람, 비공개 프로필은 지원한 팀장만 관계에 따라 열람 |
| AI 자연어 탐색·추천 전체 | 로그인 필요. 공모전·팀·사람 등 요청 대상과 관계없이 사용 불가 | [추천 정책](matching.md)의 권한·공개 범위 내에서 허용 |
| 개인 알림함 | 로그인 안내만 표시하며 개인 항목은 제공하지 않음 | [본인 소유·관계의 알림](notifications.md)만 허용 |
| 팀 공간 | 로그인 필요 | [팀장·현재 확정 팀원만 접근](team-recruitment.md#team-workspace-access) |

- 비로그인 사용자가 참여 버튼을 누르거나 프로필 작성·팀 생성·지원·AI의 주소로 직접 접근해도 같은 로그인 조건을 적용합니다. 로그인을 요청하고, 인증 없이 프로필 저장·팀 생성·지원 제출을 완료하거나 해당 내역을 만들지 않습니다.
- 로그인 성공만으로 팀을 만들거나 지원을 자동 제출하지 않습니다. 로그인 후에도 사용자가 해당 행동을 실행하고 현재 조건을 충족해야 합니다. 실패·만료 시에는 아래 [단순 안내와 재로그인 흐름](#auth-failures)을 적용합니다.
- 지원 직전 필수 프로필 확인은 특정 팀에 학년 조건이 있는 경우에만 적용하는 규칙이 아닙니다. [모든 지원에서 누락된 필수 항목의 입력을 요청](profile.md#before-application)하며, 이 결정으로 권장·선택 항목을 필수로 바꾸지 않습니다.
- 학교 인증을 요구하지 않는 것과 공고 참가 자격 충족 여부는 구분합니다. [#77의 #33 연결 결정](https://github.com/wejo-team/sku-dreamon/issues/77)에 따라 자격 정보가 부족해도 원문 확인을 안내한 뒤 일반 팀 지원으로 접수합니다. 별도 자격 확인 대기 상태를 만들지 않으며, 필수 입력·공개 상태·마감·정원·중복·소속 제한은 유지합니다. 학적·학년은 선택 입력이고 접수 성공을 자격 검증 완료로 표시하지 않습니다.
- 공개 공고·팀 모집 정보의 일반 탐색과 AI 이용 권한을 구분합니다. 2026-10-19 사용자 요청에 따라 AI 기능 전체는 로그인 후에만 이용하며, AI 아이콘·하단 탭·직접 주소 어느 경로로 접근해도 로그인 전에 대화·요청 예시 실행·결과 생성을 허용하지 않습니다. 로그인하지 않은 사용자에게 다른 사용자의 대화·결과를 보여 주지 않으며, 로그아웃·세션 만료 후에도 같은 제한을 적용합니다.
- 로그인한 사람 탐색의 검색창에서도 AI 기능으로 진입할 수 있습니다. 로그인 자체가 팀 공간·비공개 프로필의 열람 권한을 부여하지는 않습니다. [프로필 상태와 지원 팀장 예외](profile.md#visibility)를 적용합니다.
- 비공개 프로필에서 신규 지원을 시도하면 설명과 공개 전환 확인을 제공합니다. 사용자가 확인하여 공개 저장에 성공한 뒤 현재 지원 조건을 다시 확인하며, 클릭만으로 자동 공개·지원 접수하지 않습니다. 이후 비공개로 전환해도 기존 지원·소속과 지원받은 팀장의 전체 현재 프로필 열람·최신 프로필 기반 AI 검토는 유지합니다. 일반 사람 검색·AI 사람 추천에서는 제외하며, 비공개 회원 본인의 일반 AI 이용은 허용합니다.

### 교내 인증의 의미

- 로그인은 해당 서비스 계정의 접근 권한 확인이며, 교내 구성원 확인과 별개입니다. 모든 스프린트 1 계정은 교내 미인증 상태입니다.
- 화면·문서·발표에서 자체 로그인 성공을 ‘교내 인증 완료’ 또는 ‘재학 확인 완료’로 표시하지 않습니다.
- 후속으로 학교 이메일·학교 소셜 계정 인증을 도입하더라도 확인 가능한 범위는 별도로 정의합니다. 학교 계정 소유 확인만으로 현재 재학 상태·학년·전공·실명 진위까지 확인했다고 취급하지 않습니다.
- 서비스가 요구하는 것은 실명 입력이며, 신분증 등 별도 본인확인은 스프린트 1에 포함하지 않습니다.
- 이메일 주소와 인증 여부의 다른 사용자 대상 공개 기준은 [프로필 공개 범위](profile.md#visibility)를 따릅니다.
- 내 프로필의 미인증 배지는 빨간 배경과 상태 문구로 구분하며 안내 팝업의 확인·닫기는 인증 상태를 바꾸지 않습니다. 파란 인증 배지 디자인은 후속 인증 도입을 위한 표현이며 현재 계정에 인증 상태를 부여하는 기능이 아닙니다.

2026-10-21 사용자 결정으로 향후 학교 이메일 인증에 사용할 [이메일 주소·인증 완료 시각의 저장 필드](../database/identity.md#accounts)를 이번 DB 설계에 포함합니다. 학교 이메일은 로그인 아이디와 별개이며, 인증 완료 기록은 해당 주소에만 적용하고 주소 변경·삭제 시 해제합니다. 스프린트 1에서는 두 필드를 `NULL`로 유지하며, 실제 이메일 수집·발송·인증 기능과 API는 AUTH-02의 후속 범위로 남깁니다.

### 시연 계정과 로그인 안내

- 시연에서도 동일한 자체 로그인 경로를 사용하고, ‘자체 로그인 제공 · 학교 인증 미제공’으로 안내합니다.
- 시연 계정을 준비한다면 시연용임을 표시하며 교내 인증 완료 상태로 만들지 않습니다. 시연용 계정 표시와 교내 인증 상태는 서로 다른 정보입니다.
- [이슈 #53의 결정](https://github.com/wejo-team/sku-dreamon/issues/53#issuecomment-6234951428)에 따라 실제·시연 데이터 간 추천·지원·선발의 교차를 허용하며, 상세 범위는 [시연 데이터 정책](sprint-1.md#demo-data-scope)을 따릅니다. 시연 계정 표시·자체 로그인·교내 미인증 안내는 유지하며, 데이터 혼합을 인증 우회나 기존 관계별 접근 권한 확대의 근거로 사용하지 않습니다.

<a id="account-linking"></a>

### 계정 식별과 향후 소셜 연결

이번에는 식별 원칙을 적용하고, 아래 소셜 연결 흐름·화면·연동 기능은 후속 구현 범위로 둡니다.

| 정보 | 기준 |
| --- | --- |
| 서비스 사용자 | 변하지 않는 내부 고유 사용자 ID로 식별 |
| 자체 로그인 정보 | 현재 MVP에서는 계정과 같은 행에 로그인 아이디·비밀번호 해시를 저장. 내부 사용자 ID·표시 이름·이메일과 구분 |
| 프로필·소속 팀·지원 내역 | 로그인 수단이 아니라 내부 사용자 ID에 귀속 |
| 향후 소셜 로그인 정보 | 제공자와 제공자의 고유 사용자 식별자를 조합해 기존 사용자 ID에 연결. 구글은 검증된 토큰의 `sub` 사용 |
| 교내 인증 상태 | 로그인 방법과 별도로 관리하며 소셜 연결만으로 자동 승격하지 않음 |

2026-10-21 사용자 결정에 따라 자체 로그인 정보는 계정 테이블에 통합합니다. 업무 데이터가 불변 내부 사용자 ID를 참조하는 원칙은 유지하며, 컬럼·제약·가입 저장 경계는 [계정 DB 설계](../database/identity.md#accounts)를 따릅니다. 현재 자체 가입의 필수 인증 정보를 유지하고, 소셜 전용 가입의 허용 여부와 저장 변경은 후속 도입에서 검토합니다.

- 후속 연결은 기존 계정 로그인 → 설정에서 소셜 계정 연결 → 기존 계정 재인증과 소셜 계정 인증 → 같은 내부 사용자 ID에 연결하는 흐름을 기본으로 합니다.
- 이름이나 이메일이 같다는 이유만으로 계정을 자동 병합하지 않습니다. 기존 계정과 소셜 계정 양쪽의 소유권을 확인합니다.
- 하나의 소셜 계정은 하나의 서비스 사용자에만 연결할 수 있습니다. 다른 사용자에게 이미 연결됐다면 자동 이전·병합하지 않습니다.
- 기존 아이디·비밀번호 로그인은 연결 후에도 사용할 수 있습니다. 연결 해제·계정 복구·이미 별도로 가입한 두 계정의 병합 정책은 소셜 도입 전에 정하며, 이번에 구현하지 않습니다.
- 내부 사용자 ID를 유지해 기존 서비스 데이터 이관을 줄이는 설계입니다. 소셜 제공자 설정·인증 응답 검증·연결 화면 등의 후속 개발이 없어지는 것은 아닙니다.

<a id="login-identifier"></a>

### 로그인 아이디 입력

- 정규화 후 **4~24자**, ASCII 영문 소문자 `a-z`와 숫자 `0-9`만 허용합니다. 밑줄·하이픈·한글·중간 공백은 허용하지 않습니다.
- 앞뒤 공백을 제거하고 ASCII 영문 대문자를 소문자로 통일한 다음 형식·길이를 검사합니다. 가입 중복 확인·계정 저장·로그인 조회에 같은 규칙을 적용합니다. 예를 들어 ` DreamOn01 `과 `dreamon01`은 같은 로그인 아이디입니다.
- 이 정규화는 로그인 아이디에만 적용합니다. 비밀번호나 표시 이름에 소문자 변환을 적용하지 않습니다. 형식 오류·중복 여부를 안내하며 잘라 저장하거나 다른 아이디를 자동 생성하지 않습니다.

향후 이메일을 로그인 아이디로 사용할 가능성에 대비해 [DB 저장 폭](../database/identity.md#accounts)은 `varchar(320)`으로 확보합니다. 현재 입력 규칙은 유지하며, 이메일 형식·정규화·소유권 확인과 기존 아이디의 전환 정책은 도입 시 별도로 정합니다.

<a id="password-policy"></a>

### 비밀번호 입력

[#77의 표준 적용 위임](https://github.com/wejo-team/sku-dreamon/issues/77)에 따라 [NIST SP 800-63B-4 비밀번호 지침](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver)을 참고한 입력 규칙입니다. 최소 15자는 단일 요소 비밀번호 인증 기준이고, 지침이 64자 이상 수용을 권장하는 데 대해 **128자는 서비스가 선택한 상한**입니다.

- **NFC 정규화 후 Unicode 코드 포인트 기준 15~128자**를 허용합니다. 한글 등 유니코드·영문·숫자·특수문자·공백을 받을 수 있습니다.
- 대소문자와 앞뒤·중간 공백을 보존합니다. 아이디·일반 텍스트의 소문자 변환·공백 제거 규칙을 적용하지 않습니다. 가입·설정/변경·로그인은 같은 NFC 정규화로 전체 비밀번호를 처리합니다.
- 대문자·숫자·특수문자 혼합을 강제하지 않습니다. 길이가 초과되면 안내하며 입력을 조용히 잘라 저장하거나 일부만 검증하지 않습니다.
- 가입·비밀번호 설정/변경 시 흔하거나 유출된 것으로 확인된 비밀번호는 차단하고 다른 값을 선택하도록 안내합니다. 전체 비밀번호를 차단 목록과 비교하며 일부 단어가 들어 있다는 이유만으로 차단하지 않습니다. 차단 목록 공급·갱신 방식은 개발 계획에서 정합니다.
- 비밀번호 관리자·자동완성·붙여넣기를 허용하고 보기/숨기기를 제공합니다. 이 입력 정책은 해시 알고리즘·비용·로그인 제한 횟수·세션 수명을 확정하지 않습니다.

<a id="session-policy"></a>

### 로그인 유지: 서버 세션

2026-10-21 사용자 결정에 따라 스프린트 1 웹의 로그인 유지는 **PostgreSQL에 저장하는 서버 세션과 쿠키 전달 방식**을 사용합니다. 서버가 로그인 상태와 만료·회수를 관리하며, 브라우저는 계정 정보가 들어 있지 않은 예측 불가능한 세션 토큰을 쿠키로 전달합니다. 자체 아이디·비밀번호로 계정을 확인하는 방식은 유지합니다.

| 항목 | 기준 |
| --- | --- |
| 로그인 성공 | 비밀번호 검증 후 새 무작위 세션 토큰을 만들고, 서버 세션 저장에 성공한 뒤 쿠키를 발급 |
| 가입 직후 | 계정·자체 인증 정보·새 세션을 함께 저장한 뒤 자동 로그인하고 프로필 설정으로 이동. 저장 실패를 가입 성공으로 표시하지 않음 |
| 브라우저 전달 | `HttpOnly`, `Secure`, `SameSite=Lax`인 host-only 쿠키 사용. 세션 토큰을 응답 JSON이나 JavaScript 저장소에 넣지 않음 |
| 기본 로그인 유지 | 브라우저 재시작 후에도 쿠키를 보존하고, 서버에서 세션이 유효함을 확인한 뒤 로그인 상태를 복원. 별도 ‘로그인 유지’ 체크박스 없이 모든 로그인에 같은 정책 적용 |
| 서버 저장 | 내부 계정 ID에 연결한 세션과 토큰 해시를 저장. 토큰 원문을 DB·로그에 보관하지 않음 |
| 요청 인증 | 서버에서 세션 존재·회수 여부와 유휴·절대 만료를 검사. 브라우저 쿠키가 남아 있어도 무효 세션이면 인증을 거부 |
| 유휴 만료 | 해당 세션의 마지막 유효한 인증 요청으로부터 **24시간**이 지나면 만료. 최근 사용 시각을 갱신하기 전에 검사 |
| 절대 만료 | 해당 세션 발급 시각부터 **7일(168시간)**이 지나면 만료. 계속 사용해도 이 경계를 연장하지 않음 |
| 현재 권한 | 유효한 세션에서 계정 ID를 구한 뒤 현재 프로필 공개 상태·지원 관계·팀 소속을 별도로 검사 |
| 로그아웃 | 현재 세션을 서버에서 즉시 회수하고 쿠키를 삭제. 회수가 커밋된 뒤의 새 요청은 같은 토큰으로 다시 인증할 수 없음 |
| 동시 로그인 | 허용하며 각 로그인 세션을 독립적으로 관리. 새 로그인이나 한 세션의 사용·만료·로그아웃이 다른 세션의 유효 기간·회수 상태를 변경하지 않음 |
| CSRF 보호 | 로그인·로그아웃을 포함한 상태 변경 요청에 적용. `HttpOnly`·`SameSite` 속성만으로 보호가 완료됐다고 보지 않음 |

쿠키는 HTTPS 환경에서 사용합니다. 실제 쿠키 이름·경로, 로그인 전 CSRF 보호의 발급·전달·검증과 origin 설정은 [공통 API 전송 계약](../api/conventions.md#csrf-transport)을 따릅니다. 실제 운영 도메인과 키는 배포 설정으로 주입합니다. 저장 필드·제약은 [서버 세션 테이블](../database/identity.md#auth-sessions)에서 관리합니다.

두 만료 조건 중 먼저 도달한 시점부터 인증을 거부합니다. 서버 시각이 마지막 유효 요청 시각 + 24시간 또는 발급 시각 + 7일과 **같거나 늦으면** 만료이며, 한 세션의 사용으로 다른 세션의 유휴 시간을 갱신하지 않습니다. 만료된 행을 정리하지 않았더라도 인증은 거부합니다.

브라우저 재시작은 새 로그인이 아닙니다. 같은 세션의 유휴 24시간·절대 7일 기준을 그대로 검사하고, 재시작하거나 요청을 보냈다는 이유로 절대 만료 시각을 연장하지 않습니다. 쿠키의 보존 기한도 서버의 절대 만료 시각을 넘기지 않게 설정합니다. 브라우저가 쿠키를 삭제하거나 전송하지 않으면 다시 로그인해야 합니다. 세부 전송 설정은 [쿠키 계약](../api/conventions.md#session-auth)을 따릅니다.

동시 로그인 허용에 임의의 기기 수 제한이나 기존 세션 자동 축출을 추가하지 않습니다. 같은 브라우저에서 쿠키를 공유하는 탭을 별개의 로그인 세션으로 간주하지 않습니다. 소셜 로그인·네이티브 앱의 인증 전달 계약은 이번 범위에 추가하지 않습니다.

### 자체 로그인의 최소 기준

- 비밀번호는 검증된 비밀번호 해시 방식으로 저장하며 원문이나 복호화 가능한 형태로 보관하지 않습니다. 알고리즘·설정값은 개발 계획에서 정합니다.
- 로그인 시도 제한과 [서버 세션](#session-policy)의 유휴 24시간·절대 7일 만료 및 즉시 로그아웃 처리를 구현 범위에 포함합니다. 시도 제한 수치는 구현 전에 정합니다.
- 잘못된 로그인 정보로는 로그인에 성공하지 않으며, [동일하게 정규화된 아이디](#login-identifier)로 새 계정을 만들지 않습니다. 오류 안내·재시도는 [실패·만료 흐름](#auth-failures)을 따릅니다.
- 이메일을 수집·검증하지 않는 이번 흐름에는 이메일 기반 비밀번호 재설정을 전제하지 않습니다. [계정 복구](#account-recovery)는 MVP에서 제공하지 않으며, 이름 등 자기신고 정보만으로 임의 초기화하지 않습니다.

<a id="account-recovery"></a>

### 계정 복구 — MVP 제외

2026-10-21 사용자 결정에 따라 아이디·비밀번호 분실 시 복구 기능은 MVP에서 제공하지 않습니다. 복구 화면·API·운영자 수동 초기화 절차를 이번 범위에 추가하지 않습니다. 후속 도입 시 소유권 확인 수단과 복구 범위·절차를 AUTH-05에서 정하며, 이 후속 결정을 현재 가입·로그인 구현의 선행 조건으로 두지 않습니다. 계정 탈퇴·데이터 보존 정책은 이 결정으로 변경하지 않습니다.

<a id="auth-failures"></a>

### 실패·만료의 단순 안내

- 로그인 정보가 잘못되면 아이디 존재 여부와 비밀번호 불일치를 구분하지 않는 짧은 안내를 표시하고 로그인 화면에서 재입력을 받습니다.
- 세션이 만료되거나 회수되어 인증에 실패하면 로그인 상태와 개인 데이터 표시를 해제하고, 재로그인이 필요하다는 안내와 로그인 화면으로의 진입을 제공합니다. 실패한 보호 요청을 자동 반복하거나 자동으로 세션을 연장하지 않습니다.
- 인증 서버의 일시 장애·네트워크 실패를 세션 만료라고 단정하지 않습니다. 다시 시도할 수 있는 오류를 안내하며, 세션의 유효 여부와 구분합니다.
- 재로그인만으로 팀 생성·지원 제출 등 실패한 업무를 자동 실행하지 않습니다. 복잡한 자동 복귀·작성 초안 복구 흐름은 이번 결정으로 추가하지 않습니다.
- 단순한 화면 안내는 서버의 인증·권한·CSRF 검사와 로그인 시도 제한을 생략하는 뜻이 아닙니다. 구체 문구는 이 기준에 맞춰 구현하고 시도 제한 수치는 AUTH-04에서 정합니다.

## 현재 디자인 레퍼런스

## 완료 조건

다음 조건의 체크는 구현과 검증을 의미하며, 이관이나 명세 검토만으로 체크하지 않습니다.

| 기존 조건 | 이슈 #20에 따른 변경 |
| --- | --- |
| AC-01 · 실제/시연 인증 경로 가입과 상태 확인 | 이번 범위에서 대체; 자체 가입 조건은 AC-05 |
| AC-02 · 시연 인증과 실제 교내 인증 구분 | 별도 시연 인증 경로 제외로 대체; 시연 안내 조건은 AC-06 |
| AC-03 · 이메일 인증을 실명 검증으로 표시하지 않음 | 이메일 인증 제외로 대체; 검증 한계 표시 조건은 AC-07 |

- [ ] AC-04: 가입 성공 시 계정·자체 인증 정보·새 세션이 함께 저장되고, 사용자는 아이디·비밀번호를 다시 입력하지 않고 자동 로그인하여 프로필 설정으로 이동한다. 저장 실패 시 부분 가입을 성공으로 처리하거나 세션 쿠키를 발급하지 않는다.
- [ ] AC-05: 사용자가 학교 이메일·소셜 계정 없이 자체 아이디·비밀번호로 가입하고, 계정 화면에서 교내 미인증 상태를 확인할 수 있다.
- [ ] AC-06: 시연에서도 동일한 자체 로그인 경로를 사용하며, 시연 계정 사용 시 시연용 표시와 학교 인증 미제공 안내를 확인할 수 있다. 실제·시연 데이터 간 추천·지원·선발이 연결되어도 시연 표시와 기존 인증·접근 권한 조건을 유지한다.
- [ ] AC-07: 자체 로그인과 실명 입력만으로 화면·문서에서 교내 구성원·재학·실명 진위 확인을 완료했다고 표시하지 않는다.
- [ ] AC-08: 같은 계정으로 다시 로그인하면 기존 프로필·소속 팀·지원 내역이 유지되고, 로그아웃한 세션으로는 로그인 필요 동작을 수행할 수 없다.
- [ ] AC-09: 잘못된 비밀번호로 로그인하거나 중복 로그인 아이디로 가입할 수 없으며, 비밀번호 해시·로그인 시도 제한·세션 만료가 구현 검증으로 확인된다.
- [ ] AC-10: 비로그인 사용자가 공개된 공고와 팀 모집 정보의 목록·상세를 탐색할 수 있으며, 이를 위해 로그인을 요구하지 않는다.
- [ ] AC-11: 비로그인 상태에서 프로필 작성·팀 생성·지원 버튼 또는 해당 주소로 접근하면 로그인을 요청하고, 프로필 저장·팀 생성·지원 제출 내역이 생성되지 않는다. 로그인 성공만으로 팀 생성·지원 제출을 자동 실행하지 않는다.
- [ ] AC-12: 로그인한 사용자는 교내 미인증만을 이유로 프로필 작성·팀 생성·지원을 거부당하지 않는다. 자격 정보 부족은 원문 확인 안내 후 일반 지원으로 접수하되 공개 프로필·필수 입력·마감·정원·중복·소속 제한을 적용하고 자격 충족을 보장하지 않는다.
- [ ] AC-13: 로그인 후 공개 프로필의 등록된 모든 항목을 탐색할 수 있고, 비공개 프로필은 일반 검색·AI 사람 탐색·일반 상세 주소에서 제공하지 않는다. 지원한 팀장의 전체 현재 프로필 열람 예외와 팀 공간의 팀장·현재 확정 팀원 제한을 각각 적용한다.
- [ ] AC-14: 비로그인 사용자가 AI 아이콘·하단 탭·직접 주소로 접근하면 로그인 안내를 확인하고 공모전·팀·사람 요청 모두를 실행할 수 없다. 로그아웃·세션 만료 이후에도 대화·결과를 제공하거나 요청을 실행하지 않으며, 로그인 후에는 허용된 범위에서 이용할 수 있다.
- [ ] AC-15: 내 프로필의 교내 미인증 배지로 학교 인증 미제공 안내를 열고 닫을 수 있으며, 팝업을 확인하거나 로그인해도 교내 인증 완료 상태로 바뀌지 않는다.
- [ ] AC-16: 아이디는 앞뒤 공백 제거·ASCII 대문자 소문자화 후 영문 소문자/숫자 4~24자로 검증한다. 가입과 로그인에 같은 정규화를 적용해 대소문자·외부 공백만 다른 아이디의 중복 가입을 막고 중간 공백·밑줄·하이픈을 거부한다.
- [ ] AC-17: 비밀번호는 NFC 후 코드 포인트 15~128자이며 대소문자·공백을 보존한다. 혼합 문자를 강제하지 않고 가입·설정/변경 때 차단 목록을 확인한다. 전체 값을 검증하며 비밀번호 관리자·자동완성·붙여넣기를 허용한다.
- [ ] AC-18: 로그인 성공 시 새 서버 세션이 저장된 뒤 지정된 보안 속성의 쿠키가 발급된다. 세션 저장 실패 시 로그인 성공을 반환하지 않으며, 토큰 원문이 응답 JSON·JavaScript 저장소·DB·로그에 남지 않는다.
- [ ] AC-19: 서버가 마지막 유효 인증 요청 후 24시간과 세션 발급 후 7일 중 먼저 도달한 시점부터 인증을 거부한다. 현재 세션 로그아웃은 서버 회수 커밋 즉시 효력이 생기며, 만료·회수된 세션은 쿠키가 남아 있어도 보호된 조회·변경을 수행하거나 후속 요청으로 되살아날 수 없다.
- [ ] AC-20: 로그인·로그아웃을 포함한 상태 변경 요청에서 CSRF 보호가 검증되며, 검증에 실패한 요청으로 세션을 발급·회수하거나 업무 데이터를 변경하지 않는다.
- [ ] AC-21: 같은 계정으로 동시에 로그인한 세션이 독립적으로 동작한다. 새 로그인과 한 세션의 사용·만료·로그아웃이 다른 세션을 종료하거나 그 세션의 유효 기간을 연장하지 않는다.
- [ ] AC-22: 잘못된 로그인 정보는 짧은 공통 안내 후 재입력할 수 있고, 만료·회수된 세션은 개인 데이터 표시를 해제한 뒤 재로그인을 안내한다. 일시 장애를 만료로 처리하거나 실패한 업무를 자동 실행하지 않는다.
- [ ] AC-23: 별도 로그인 유지 선택 없이 브라우저 재시작 후 쿠키가 남아 있으면 서버에서 같은 세션을 검사한다. 유효한 세션은 로그인 상태를 복원하고, 유휴 24시간·절대 7일 만료 또는 회수된 세션은 재로그인을 안내한다. 재시작으로 절대 만료 시각이 연장되지 않는다.

소셜 로그인·연결 화면은 스프린트 1 완료 조건에 포함하지 않습니다. 업무 데이터가 로그인 아이디 대신 불변 계정 ID를 참조하는지는 개발 계획·데이터 모델 리뷰에서 확인하고, 실제 소셜 연결·해제 완료 조건은 도입 시 추가합니다.

## 2026-10-24 인증 운영 기준

사용자가 다음 구현 기준을 채택했습니다. PostgreSQL에 시도 횟수를 저장해 프로세스 간 제한을 공유합니다. 로그인은 정규화 아이디별 15분당 10회, 직접 접속 IP별 15분당 100회로 제한합니다. 계정 존재·비밀번호 성공 여부와 관계없이 시도에 적용하며 만료 후 다시 시도할 수 있습니다. 프록시 헤더를 무조건 신뢰하지 않습니다. 가입·아이디 확인은 각각 IP 기준으로 설정 가능한 별도 제한을 둡니다(초기 설정: 가입 15분당 10회, 확인 15분당 100회). 각 창의 첫 시도부터 15분을 계산하고 제한 시 429와 Retry-After를 반환합니다.

비밀번호 차단 목록은 운영자가 관리·교체하는 UTF-8 로컬 파일과 버전 설정으로 공급합니다. 미설정이면 가입은 503으로 거부하고 기존 계정 로그인은 유지합니다. 설정한 파일을 읽을 수 없거나 비어 있으면 앱 시작을 실패시켜 누락을 드러냅니다. 목록 교체 후 앱을 재시작합니다. 실제 목록 공급·운영 키·origin 배포는 별도 운영 작업입니다.
