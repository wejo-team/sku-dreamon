# 가입과 로그인

- 구현 상태: 예정
- 명세 검토: [PR #14](https://github.com/wejo-team/wejo-app/pull/14), PDF 대조·명세 연결 보완 [PR #17](https://github.com/wejo-team/wejo-app/pull/17)
- 정책 변경: [이슈 #20 · 자체 로그인과 향후 계정 연결](https://github.com/wejo-team/wejo-app/issues/20)
- 구현 작업: 미등록

기획 원문의 가입·인증 요구사항 중 스프린트 1 가입 경로를 이슈 #20의 결정으로 변경합니다. 서비스 자체 아이디·비밀번호로 가입하고 로그인하며, 학교 인증·이메일 인증·소셜 로그인은 후속 범위로 미룹니다. 문서 반영과 기능 구현 완료는 구분합니다.
프로필의 이름·공개 범위를 변경할 때만 [프로필 정책](profile.md)을 함께 읽습니다.

## 목적과 사용자

교내 공모전 참여를 원하는 사용자가 서비스 계정을 만들고 로그인한 뒤 프로필 설정과 참여 흐름을 시작할 수 있게 합니다. 스프린트 1에서는 교내 구성원 여부를 검증하지 않으므로 로그인만으로 교내 사용자임을 보장하지 않습니다.

## 범위

| 항목 | 스프린트 1 범위 |
| --- | --- |
| 자체 회원가입·로그인 | 서비스 로그인 아이디와 비밀번호로 가입·로그인·로그아웃 |
| 상태 표시 | 로그인 상태와 교내 미인증 상태를 구분 |
| 학교·이메일 인증 | 이번 범위에서 제외; 학교 이메일 입력·인증 메일 수신을 가입 조건으로 요구하지 않음 |
| 소셜 로그인·계정 연결 | 이번 범위에서 제외; 기존 사용자 계정에 나중에 연결할 수 있도록 계정 식별 원칙만 정의 |
| 시연 | 같은 자체 로그인 사용; 별도 인증 우회·가짜 인증 성공 경로를 제공하지 않음 |
| 별도 본인확인 | 신분증 등을 통한 실명 진위 확인은 제외 |

가입 후 필수 프로필 작성은 [프로필 입력 항목](profile.md#fields)에서 정의합니다. 비밀번호 정책·계정 복구·세션 방식, API·DB·라이브러리 상세는 아래 미정 사항과 개발 계획에서 다룹니다.

<a id="login-decision"></a>

## AUTH-01 결정과 적용 환경

스프린트 1을 실행하는 개발·시연·배포 환경의 사용자 가입 경로는 자체 아이디·비밀번호 방식으로 통일합니다. 배포 여부나 공개 모집 범위를 이 결정으로 확정하지는 않습니다.

| 결정 | 이유와 영향 |
| --- | --- |
| 자체 로그인으로 핵심 흐름 검증 | 학교 메일 발송·학교 계정 정책·소셜 제공자 연동을 이번 개발의 선행 조건에서 제외 |
| 학교 인증은 후속 검토 | 교내 구성원만 가입할 수 있다고 안내할 수 없으며, 로그인 성공으로 교내 인증 완료 표시를 부여하지 않음 |
| 메일 발송을 요구하지 않는 가입 | 인증 메일 발송 비용·설정이 이번 가입 흐름에 필요하지 않음. 서버·DB 운영과 계정 보안·복구 부담은 별도 |
| 내부 사용자 ID 유지 | 나중에 로그인 수단을 추가해도 기존 프로필·소속 팀·지원 내역의 소유자를 유지 |

기존 원문의 ‘실제 학교 이메일 인증 또는 시연 인증’ 선택은 이 결정으로 대체합니다. 실제 계정의 비밀번호를 확인하는 로그인은 구현 대상이며, 학교 인증을 생략하는 것을 로그인 보안 생략으로 취급하지 않습니다.

## 사용자 흐름과 동작

1. 사용자가 회원가입 화면에서 로그인 아이디와 비밀번호를 등록합니다. 이메일·구글 계정은 요구하지 않습니다.
2. 가입한 계정으로 로그인하고 프로필 설정 흐름에서 필수 정보를 작성합니다. 가입 직후 자동 로그인 여부는 개발 계획에서 정합니다.
3. 계정 화면에서 로그인 상태와 별도로 ‘교내 미인증 · 학교 인증은 아직 제공하지 않습니다’ 안내를 확인합니다. 정확한 UI 문구는 같은 의미를 유지합니다.
4. 로그아웃하면 현재 로그인 세션이 종료되고, 다시 로그인하면 같은 프로필·팀·지원 내역으로 이어집니다.

비로그인 사용자의 공고 탐색·참여 허용 범위와 프로필 미완성 시 행동은 각각 AUTH-03과 [프로필 미정 사항](profile.md#open-questions)에서 결정합니다.

## 정책과 예외

<a id="verification-meaning"></a>

### 교내 인증의 의미

- 로그인은 해당 서비스 계정의 접근 권한 확인이며, 교내 구성원 확인과 별개입니다. 모든 스프린트 1 계정은 교내 미인증 상태입니다.
- 화면·문서·발표에서 자체 로그인 성공을 ‘교내 인증 완료’ 또는 ‘재학 확인 완료’로 표시하지 않습니다.
- 후속으로 학교 이메일·학교 소셜 계정 인증을 도입하더라도 확인 가능한 범위는 별도로 정의합니다. 학교 계정 소유 확인만으로 현재 재학 상태·학년·전공·실명 진위까지 확인했다고 취급하지 않습니다.
- 서비스가 요구하는 것은 실명 입력이며, 신분증 등 별도 본인확인은 스프린트 1에 포함하지 않습니다.
- 이메일 주소와 인증 여부의 다른 사용자 대상 공개 기준은 [프로필 공개 범위](profile.md#visibility)를 따릅니다.

<a id="demo-auth"></a>

### 시연 계정과 로그인 안내

- 시연에서도 동일한 자체 로그인 경로를 사용하고, ‘자체 로그인 제공 · 학교 인증 미제공’으로 안내합니다.
- 시연 계정을 준비한다면 시연용임을 표시하며 교내 인증 완료 상태로 만들지 않습니다. 시연용 계정 표시와 교내 인증 상태는 서로 다른 정보입니다.
- 시연 계정·공고·팀과 실제 데이터의 상호작용 허용 범위는 [이슈 #53](https://github.com/wejo-team/wejo-app/issues/53)에서 결정합니다. 자체 로그인을 제공한다는 이유만으로 실제 데이터 접근을 허용하지 않습니다.

<a id="account-linking"></a>

### 계정 식별과 향후 소셜 연결

이번에는 식별 원칙을 적용하고, 아래 소셜 연결 흐름·화면·연동 기능은 후속 구현 범위로 둡니다.

| 정보 | 기준 |
| --- | --- |
| 서비스 사용자 | 변하지 않는 내부 고유 사용자 ID로 식별 |
| 자체 로그인 정보 | 로그인 아이디·비밀번호 해시를 사용자 ID에 연결. 표시 이름·이메일과 구분 |
| 프로필·소속 팀·지원 내역 | 로그인 수단이 아니라 내부 사용자 ID에 귀속 |
| 향후 소셜 로그인 정보 | 제공자와 제공자의 고유 사용자 식별자를 조합해 기존 사용자 ID에 연결. 구글은 검증된 토큰의 `sub` 사용 |
| 교내 인증 상태 | 로그인 방법과 별도로 관리하며 소셜 연결만으로 자동 승격하지 않음 |

- 후속 연결은 기존 계정 로그인 → 설정에서 소셜 계정 연결 → 기존 계정 재인증과 소셜 계정 인증 → 같은 내부 사용자 ID에 연결하는 흐름을 기본으로 합니다.
- 이름이나 이메일이 같다는 이유만으로 계정을 자동 병합하지 않습니다. 기존 계정과 소셜 계정 양쪽의 소유권을 확인합니다.
- 하나의 소셜 계정은 하나의 서비스 사용자에만 연결할 수 있습니다. 다른 사용자에게 이미 연결됐다면 자동 이전·병합하지 않습니다.
- 기존 아이디·비밀번호 로그인은 연결 후에도 사용할 수 있습니다. 연결 해제·계정 복구·이미 별도로 가입한 두 계정의 병합 정책은 소셜 도입 전에 정하며, 이번에 구현하지 않습니다.
- 내부 사용자 ID를 유지해 기존 서비스 데이터 이관을 줄이는 설계입니다. 소셜 제공자 설정·인증 응답 검증·연결 화면 등의 후속 개발이 없어지는 것은 아닙니다.

### 자체 로그인의 최소 기준

- 비밀번호는 검증된 비밀번호 해시 방식으로 저장하며 원문이나 복호화 가능한 형태로 보관하지 않습니다. 알고리즘·설정값은 개발 계획에서 정합니다.
- 로그인 시도 제한, 세션 만료와 로그아웃 처리를 구현 범위에 포함합니다. 제한 수치와 세션 방식·기간은 구현 전에 정합니다.
- 잘못된 로그인 정보로는 로그인에 성공하지 않으며, 기존 사용자와 같은 로그인 아이디로 새 계정을 만들지 않습니다. 아이디 정규화·오류 문구·재시도 흐름은 AUTH-04에서 정합니다.
- 이메일을 수집·검증하지 않는 이번 흐름에는 이메일 기반 비밀번호 재설정을 전제하지 않습니다. 계정 복구는 AUTH-05에서 결정하며, 이름 등 자기신고 정보만으로 임의 초기화하지 않습니다.

### 아직 정의되지 않은 실패 흐름

로그인 실패·세션 만료·재시도·중복 아이디의 상세 안내와 복구 흐름은 구현 전에 정해야 합니다. 미정 사항을 해결하기 전에는 구체적인 제한 횟수나 유효기간을 확정 정책으로 사용하지 않습니다.

<a id="acceptance-criteria"></a>

## 완료 조건

다음 조건의 체크는 구현과 검증을 의미하며, 이관이나 명세 검토만으로 체크하지 않습니다.

| 기존 조건 | 이슈 #20에 따른 변경 |
| --- | --- |
| AC-01 · 실제/시연 인증 경로 가입과 상태 확인 | 이번 범위에서 대체; 자체 가입 조건은 AC-05 |
| AC-02 · 시연 인증과 실제 교내 인증 구분 | 별도 시연 인증 경로 제외로 대체; 시연 안내 조건은 AC-06 |
| AC-03 · 이메일 인증을 실명 검증으로 표시하지 않음 | 이메일 인증 제외로 대체; 검증 한계 표시 조건은 AC-07 |

- [ ] AC-04: 가입을 마친 사용자가 프로필 설정 흐름을 시작할 수 있다.
- [ ] AC-05: 사용자가 학교 이메일·소셜 계정 없이 자체 아이디·비밀번호로 가입하고, 계정 화면에서 교내 미인증 상태를 확인할 수 있다.
- [ ] AC-06: 시연에서도 동일한 자체 로그인 경로를 사용하며, 시연 계정 사용 시 시연용 표시와 학교 인증 미제공 안내를 확인할 수 있다.
- [ ] AC-07: 자체 로그인과 실명 입력만으로 화면·문서에서 교내 구성원·재학·실명 진위 확인을 완료했다고 표시하지 않는다.
- [ ] AC-08: 같은 계정으로 다시 로그인하면 기존 프로필·소속 팀·지원 내역이 유지되고, 로그아웃한 세션으로는 로그인 필요 동작을 수행할 수 없다.
- [ ] AC-09: 잘못된 비밀번호로 로그인하거나 중복 로그인 아이디로 가입할 수 없으며, 비밀번호 해시·로그인 시도 제한·세션 만료가 구현 검증으로 확인된다.

소셜 로그인·연결 화면은 스프린트 1 완료 조건에 포함하지 않습니다. 계정 식별과 로그인 수단의 분리는 개발 계획·데이터 모델 리뷰에서 확인하고, 실제 소셜 연결·해제 완료 조건은 도입 시 추가합니다.

## 미정 사항

| ID | 결정할 내용 | 결정이 필요한 이유 |
| --- | --- | --- |
| AUTH-02 | 후속 학교 인증의 대상 이메일 도메인·대상 구성원·수단. 구성원 범위는 [이슈 #21](https://github.com/wejo-team/wejo-app/issues/21) | 이번 자체 로그인으로 교내 소속·재학 자격을 보장하지 않음 |
| AUTH-03 | 비로그인 사용자의 화면·행동 허용 범위, 교내 미인증 상태와 접근 권한의 관계. [이슈 #40](https://github.com/wejo-team/wejo-app/issues/40) | 로그인 여부와 학교 인증 여부를 분리해 접근 표를 작성해야 함; 로그인만으로 다른 사람의 프로필 전체 열람 권한을 부여하지 않음 |
| AUTH-04 | 로그인 아이디 형식·정규화, 비밀번호 조건, 실패·만료·재시도·중복 아이디 안내와 복귀 흐름 | 최소 기준 아래 상세 동작·수치를 구현 전에 결정해야 함 |
| AUTH-05 | 아이디·비밀번호 분실 시 복구 수단·소유권 확인·안내 및 초기 운영 범위 | 미검증 이메일이나 자기신고만으로 계정을 복구할 수 없으며, 구현 전에 정책을 정해야 함 |

AUTH-01은 위 [결정과 적용 환경](#login-decision)으로 옮겼습니다. 이슈 #20 해결은 가입 경로의 결정이며, 남은 정책 결정·기능 구현의 완료를 뜻하지 않습니다.
