## 목적과 사용자

AI 기반 교내 공모전 도전 지원 서비스의 첫 흐름을 만듭니다. 사용자는 로그인 없이 공개 공고·팀 모집 정보를 탐색하고, 자체 로그인 후 팀을 만들거나 기존 팀에 지원합니다. 모든 지원의 제출 직전에 누락된 필수 정보를 보완하며, 이번 범위에서는 교내 구성원 여부를 검증하지 않습니다. 팀장은 실제 지원자를 검토·선발하고, 사용자는 추천과 자신의 지원 결과를 확인합니다. 공고는 [최초 공개 조건](contests.md#publication-policy)을 따릅니다. 확인된 JSON 신규 적재 CLI와 운영 수집·갱신·관리자 UI의 미정 범위는 [공고 운영 경로](contests.md#operation-flow)에서 구분합니다.

팀장이 선발하면 해당 지원자가 즉시 확정 팀원이 되며 별도 수락은 없습니다. 팀장 포함 정원과 선발 시 차감은 [팀원 확정과 정원 정책](team-recruitment.md#membership-capacity)을 따릅니다. 팀 모집 상태는 [모집 중·모집 마감 두 가지](team-recruitment.md#team-state-transitions)이며 검토 시작·선발·미선발은 개별 지원에 적용합니다. [검토 중에도 현재 접수 조건을 충족하면 신규 지원을 받으며](team-recruitment.md#recruitment-review), 팀 모집 종료·기한 경과 뒤 기존 지원 선발은 [공고 접수 마감 전·여석 등 현재 조건](team-recruitment.md#selection-window)을 따릅니다.

모든 팀의 목표 총 정원은 [공고의 참가 인원 범위](team-recruitment.md#official-capacity)에 맞추며, 1명 공고는 추가 모집 없이 운영합니다. 준비 모임 예외와 개인/팀 참가 방식의 별도 관리는 제거합니다. 마감은 [원문 시각·시간대를 우선하고 누락 시 한국시간·해당 날짜 종료로 보완](contests.md#deadline-policy)하며 원문 값과 보완 여부를 API에 보존합니다. 상세의 시각 보완 설명 문단은 표시하지 않습니다.

팀 생성·선발에는 팀장을 포함한 [공모전별 한 팀 소속 제한](team-recruitment.md#membership-limit)을 적용하며, 같은 공모전 소속 중 신규 지원은 받지 않습니다. 지원자는 선발·확정 후에도 [지원을 취소해 팀에서 빠지고 한 자리를 반환](team-recruitment.md#application-cancellation)할 수 있습니다. 취소·폐기 뒤에는 현재 무소속·모집 조건을 충족하면 새 지원이 가능하고, 미선발된 같은 팀에는 재지원할 수 없는 [종료 사유별 정책](team-recruitment.md#reapplication)을 적용합니다. 같은 공모전의 여러 팀에 [동시 지원](team-recruitment.md#parallel-applications)할 수 있고 선발·본인 팀 생성 성공 시 같은 공모전의 다른 대기 지원을 함께 폐기합니다. 다른 공모전·종료된 지원은 유지하며 소속 취소 후 자동 복원하지 않습니다. 모집은 [팀장이 명시적으로 재개](team-recruitment.md#recruitment-reopening)하며 자리 반환으로 자동 재개하지 않습니다. 팀장 변경·위임·선발 취소·강퇴·탈퇴·팀 삭제는 [MVP 제외](team-recruitment.md#membership-exclusions)입니다.

## AI와 알고리즘의 역할

추천은 LLM 기반이며 백엔드의 실행 구조·입력·저장은 [AI 아키텍처](../development/ai-architecture.md)에 구현 범위를 명시합니다. 제품 화면은 [PR #192](https://github.com/wejo-team/sku-dreamon/pull/192)에서 실제 API에 연결했습니다. 화면의 브라우저 통합 검사는 시험 모델을 사용하며 실제 제공자를 추가로 호출하지 않았습니다. 실제 모델을 사용한 화면 통합 검사·자료 품질 평가·운영 배포는 후속입니다. 기존 서버의 제공자 호출 검증과 이번 화면 검증은 [구현 현황](../development/implementation-status.md)에서 구분합니다. 추천과 실제 참여 권한·접수 제한은 구분합니다. 긴 문서를 읽기 쉽게 정리하는 공고 요약은 별도 활용 후보이며, [#38의 보류 판단](contests.md#summary-scope)에 따라 요약의 사용처·필요성과 MVP 포함 여부를 화면 기획 때 먼저 정하고 AI 연동 여부는 그 뒤에 결정합니다.

| 기능 | 처리 기준 | 담당 명세 |
| --- | --- | --- |
| 참가 자격 확인 | 넓은 참가 대상 분류와 원문 조건 안내. 참가 자격은 비즈니스 로직의 차단 조건으로 사용하지 않고 원문 확인 안내 제공. 마감·정원·공개·중복·소속 등 서비스 제한은 유지 | [추천 매칭](matching.md) |
| 마감 여부 확인 | 날짜와 상태 기반 처리 | [공고](contests.md), [팀 모집과 지원](team-recruitment.md) |
| 공모전·팀·지원자 추천 | LLM 기반 후보 제안·근거. 고정 점수·기존 산식 제외. 백엔드·제품 화면의 실제 API 연결과 품질 평가·운영 후속을 구분 | [추천 매칭](matching.md) |
| 공고 요약 | 사용처·필요성·MVP 포함 여부는 TBD. 포함 시 내용·생성 방식·표시 기준을 정하고 실제 AI 연동은 이후 결정. 참가 조건 정리와 최초 공개 조건은 유지 | [요약 범위](contests.md#summary-scope) |
| 매칭 이유 | 현재 확인 가능한 데이터와 요청 조건에 근거한 설명, 공개 범위 준수 | [추천 매칭](matching.md) |

작업 분해·역할 초안과 회의 시간 계산은 위 후속 범위에 둡니다. LLM이 확인되지 않은 자격·경험·역량·시간 겹침을 사실처럼 만들거나 지원·선발을 자동 확정하지 않습니다. 공식 디자인의 예시 응답은 실제 모델 연동이나 확정 아키텍처가 아닙니다.

별도 공고 요약 영역은 현재 화면 목록에 정의되어 있지 않습니다. 화면 기획 때 사용처·필요성과 MVP 포함 여부를 먼저 정하며, 공모전 상세에 요약을 추가하거나 제외하는 것으로 확정하지 않습니다.

### 탐색 목록의 페이지 이동

탐색의 **공모전·팀·사람** 탭은 페이지 번호를 선택하는 페이지네이션으로 제공합니다. 이 목록에 커서 기반 무한 스크롤이나 더보기 버튼을 적용하지 않습니다.

| 상황 | 동작 |
| --- | --- |
| 결과 표시 | 현재 검색어·필터·정렬과 열람 권한을 적용한 전체 검색 결과 수, 현재 페이지와 총페이지를 표시. 현재 페이지에 표시한 개수를 전체 결과 수로 표기하지 않음 |
| 페이지 이동 | 선택한 페이지의 결과로 교체. 최대 5개의 연속 페이지 번호와 처음·이전·다음·마지막 이동을 제공하고 현재 페이지를 구분. 첫 페이지의 처음·이전과 마지막 페이지의 다음·마지막 이동은 불가 |
| 검색·필터·정렬·탭 변경 또는 조건 초기화 | 변경한 조건의 1페이지부터 표시. 초기화는 현재 탭을 유지 |
| 상세에서 복귀 | 진입 전 탐색 탭·검색어·필터·정렬·페이지를 유지. 현재 권한과 최신 조회 결과는 다시 적용 |
| 결과 없음 | 결과 0건과 조건 변경·초기화를 안내하고 이동할 페이지가 있는 것처럼 페이지 선택을 제공하지 않음 |
| 잘못된 페이지·결과 감소 | 양의 정수가 아닌 페이지는 1페이지로, 결과가 있는 상태에서 마지막 페이지를 넘으면 유효한 마지막 페이지로 보정. 결과가 없어지면 빈 결과 상태로 처리 |

사람 탐색의 결과 수는 로그인 후 일반 탐색에서 열람 가능한 공개 프로필만 집계합니다. 비공개 사용자나 지원 팀장 예외로만 열람하는 사람을 전체 검색 결과 수에 포함하지 않습니다. 검색 결과 수는 서비스 전체 회원 수를 뜻하지 않습니다.

페이지 이동 컨트롤에는 목적과 현재 페이지를 알 수 있는 접근성 이름·상태를 제공하고, 모바일에서 각 조작 영역을 최소 44×44px로 확보합니다. 2026-10-28 사용자 요청에 따라 제품 공모전 탐색은 카드를 간결하게 만들고 페이지당 12개를 표시합니다. 팀·사람 탐색과 공모전 상세의 팀 목록은 기존 6개를 유지합니다. 페이지 크기와 총페이지 계산은 같은 값을 사용하며, 서버 조회·집계는 [API 페이지 계약](../api/conventions.md#pagination)을 따릅니다. 이전 스크롤 위치 복원은 별도이며, 팀 생성의 공모전 선택 팝업에서 사용하는 결과 추가 표시는 변경하지 않습니다.

## 모바일 웹과 시연 기준

- **모바일 우선 반응형 웹 서비스**로 제공합니다. 문서와 발표에서도 이 표현을 사용합니다.
- 브라우저에서 URL로 접속하며 별도 설치 없이 시연합니다. 공식 디자인은 모바일 화면을 기준으로 하며 별도 데스크톱 서비스 화면은 만들지 않습니다. 넓은 브라우저에서는 모바일 화면을 가운데 배치해 확인할 수 있게 합니다.
- 로그인, 프로필, 공고 탐색, 팀 모집·지원, 팀장 관리를 웹 페이지로 제공하고 버튼·입력창·목록·상태 표시가 실제로 동작해야 합니다.
- 구체적인 모바일 UI 개발 기준은 [프론트엔드 가이드](../development/frontend.md)의 「모바일 UI」 절을 따릅니다.

| 시연 항목 | 기준 |
| --- | --- |
| 접속 | 배포된 웹 URL 또는 개발 서버 |
| 기본 시연 | 스마트폰 브라우저 |
| 보조 시연 | 데스크톱 브라우저의 모바일 화면 |
| 데이터 | [실제·시연 계정·공고·팀 간 추천·지원·선발 허용](#demo-data-scope). 시연 데이터임을 표시하며 사용할 수·선정·준비 방식은 후속 결정 |
| 로그인 | 동일한 자체 로그인 경로를 사용하며 학교 인증 미제공·시연 계정 여부를 안내. [시연 계정 안내](authentication.md#demo-auth)를 따름 |
| AI | 실제 LLM API 연동 여부를 사실대로 안내. 추천은 LLM 기반 구현 대상이며 공고 요약의 포함 여부·연동은 별도 TBD |

공식 디자인에는 제품 사용에 관계없는 “시안·개발 환경·미연동” 배너를 상시 표시하지 않습니다. 저장소의 디자인 설명에는 로컬 예시 데이터·모의 응답과 구현되지 않은 연결을 명시합니다. 이 디자인 문서화와 실제 서비스 시연의 시연 계정·데이터·AI 연동 사실 안내는 목적이 다르며, 디자인에서 배너를 생략한 것을 실제 서비스에서 시연 데이터를 숨기는 근거로 사용하지 않습니다.

### 실제·시연 데이터의 상호작용

[이슈 #53의 결정](https://github.com/wejo-team/sku-dreamon/issues/53#issuecomment-6234951428)에 따라 **실제·시연 계정·공고·팀을 서로 추천·지원·선발할 수 있게 허용**합니다. 시연 데이터라는 이유만으로 별도 후보 집합으로 분리하거나 상호작용을 차단하지 않습니다.

| 이용 계정 | 대상 공고·팀 | 추천·지원 |
| --- | --- | --- |
| 실제 계정 | 실제 공고·팀 | 기존 추천·접수 조건을 충족하면 허용 |
| 실제 계정 | 시연 공고·팀 | 기존 추천·접수 조건을 충족하면 허용 |
| 시연 계정 | 실제 공고·팀 | 기존 추천·접수 조건을 충족하면 허용 |
| 시연 계정 | 시연 공고·팀 | 기존 추천·접수 조건을 충족하면 허용 |

실제·시연 팀의 팀장은 해당 팀에 지원한 실제·시연 계정을 모두 검토·선발할 수 있습니다. 명세의 ‘실제 지원자’는 해당 팀에 지원한 후보를 뜻하며, 시연 계정을 제외한다는 의미로 사용하지 않습니다.

- [최초 공개 조건](contests.md#publication-policy), 마감·정원·공모전별 소속 제한과 기존 추천·접수·선발 조건을 동일하게 적용합니다. 참가 자격은 원문 확인 안내를 제공하고 비즈니스 로직으로 차단하지 않는 최신 정책을 적용합니다. 혼합 허용으로 LLM 내부 아키텍처를 확정하지 않습니다.
- [자체 로그인·시연 계정 안내](authentication.md#demo-auth), 프로필 공개 범위와 팀 공간 접근 권한을 유지합니다. 시연 계정이라는 이유로 인증이나 관계별 권한을 우회하지 않습니다.
- 사용자에게 계정·공고·팀을 보여 주고 추천·지원·선발하는 흐름에서 시연용임을 구분해 안내합니다. 시연 데이터를 실제 모집이나 교내 인증 완료로 오해하게 표시하지 않습니다. 표시 연결은 [PR #177](https://github.com/wejo-team/sku-dreamon/pull/177)에서 서버 `isDemo`에 따른 `시연 계정`·`시연 공고`·`시연 팀` 배지로 구현·검증해 병합했습니다. 목록·상세·본인 프로필·팀 공간·지원자/팀원과 결정 안내에 적용합니다. 해당 DTO에 시연 필드가 없으면 이름·ID로 추정하지 않습니다.

2026-10-21 사용자 결정으로 시연 데이터는 시드 정의의 **대상 종류·고정 UUID 목록**으로 식별하며, 계정·공고·팀 테이블에 `is_demo` 컬럼을 두지 않습니다. 서버는 같은 목록에서 API의 `isDemo`를 계산하고, 이름·로그인 아이디의 네이밍 규칙은 사람이 알아보는 보조 수단으로만 사용합니다. 시드 적재와 표시 판정이 같은 UUID 목록을 참조하도록 하며, 이름을 바꾸어도 시연 여부는 바뀌지 않습니다.

사용할 계정·공고·팀의 수와 선정, 시드 추가·교체·정리 절차 및 새 데이터의 시연 분류 기준은 미정입니다. 고정 UUID는 정리 대상을 찾는 기준이며, 실제 계정과 연결된 지원·소속·알림의 삭제·보존 정책을 대신하지 않습니다. 혼합 허용은 시연 계정의 별도 로그인 기능을 채택하는 결정이 아닙니다.

## 전체 흐름의 완료 조건

기능별 예외·정책의 상세 완료 조건은 담당 명세에서 관리합니다. 아래 체크는 문서 이관 여부가 아닌 실제 구현과 검증 결과를 뜻합니다.

| 기존 조건 | 이슈 #20에 따른 변경 |
| --- | --- |
| AC-01 · 실제 교내 인증 또는 시연용 인증 가입 | 자체 로그인 경로로 대체; 새 조건은 AC-11 |
| AC-10 · 실제/시연 인증과 AI 연동 구분 | 인증 경로 변경으로 대체; 새 조건은 AC-12 |

- [ ] AC-02: 사용자가 필수 프로필을 작성하고 저장된 정보를 수정할 수 있다.
- [ ] AC-03: 사용자가 등록된 공모전 목록과 상세 정보를 확인할 수 있다.
- [ ] AC-04: 사용자가 공모전을 선택해 팀을 탐색하거나 모집글을 작성할 수 있다.
- [ ] AC-05: 사용자가 모집글에 지원하고 팀장은 해당 지원자 목록을 확인할 수 있다.
- [ ] AC-06: 시스템이 조건에 맞는 팀 또는 실제 지원자 후보를 근거와 함께 보여 준다.
- [ ] AC-07: 팀장이 지원자를 선발하고 지원자는 본인의 결과를 확인할 수 있다.
- [ ] AC-08: 팀장과 현재 확정 팀원만 팀 공간에서 공모전 정보·팀원·모집 및 매칭 상태를 확인할 수 있다. [팀 공간 접근 정책](team-recruitment.md#team-workspace-access)에 따라 팀장은 생성 시, 팀원은 선발·확정 즉시 접근하며, 지원 취소로 팀에서 이탈하면 접근이 종료된다. 공개 모집글·상세 열람과 구분하며 프로필 전체 공개 상태와 지원 팀장 예외를 적용한다.
- [ ] AC-09: 스마트폰 브라우저에서 주요 흐름을 설치 없이 이용하고, 넓은 브라우저에서는 같은 모바일 디자인과 주요 동작을 확인할 수 있다. 별도 데스크톱 화면은 범위에 포함하지 않는다.
- [ ] AC-11: 사용자가 학교 이메일·소셜 계정 없이 자체 아이디·비밀번호로 가입·로그인·로그아웃하고, 교내 미인증 상태를 확인할 수 있다. 상세 조건은 [인증 AC-04~09](authentication.md#acceptance-criteria)를 따른다.
- [ ] AC-12: 시연에서 자체 로그인 제공·학교 인증 미제공·시연 계정 여부와 실제 AI API 연동 여부가 사실에 맞게 표시된다. LLM 추천의 실제 연동과 모의 응답을 구분하며, 공고 요약의 포함 여부는 별도로 [#38의 요약 범위 결정](contests.md#summary-scope)을 따른다.
- [ ] AC-13: [시연 데이터 정책](#demo-data-scope)의 네 조합에서 기존 조건을 충족하면 추천·지원할 수 있고, 팀장은 실제·시연 구분과 무관하게 해당 팀의 지원자를 선발할 수 있다. 시연 데이터임을 확인할 수 있으며, 마감·정원·소속 제한이나 접근 권한 위반은 기존 정책대로 처리한다.
- [ ] AC-14: 탐색의 공모전·팀·사람 목록에서 현재 조건과 권한에 맞는 전체 결과 수·총페이지를 확인하고 페이지 번호로 이동할 수 있다. 조건·탭 변경 시 1페이지로 이동하고, 상세 복귀 시 조건과 페이지를 유지한다. 빈 결과와 잘못된 페이지·결과 감소는 [페이지 이동 정책](#exploration-pagination)에 맞게 처리한다.
