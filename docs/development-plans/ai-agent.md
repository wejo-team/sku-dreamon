# AI 에이전트 SDD

- 작성 기준: 2026-10-25 사용자 결정과 현재 저장소
- 상태: **명세 기반 개발(SDD)을 위한 설계 초안 · 상세 구조 미승인 · 미구현**
- 기준 명세: [LLM 기반 추천](../specs/matching.md#acceptance-criteria), AC-16~34
- 계약 원본: [AI API](../api/ai.md), [AI 저장 경계](../database/decisions.md#ai-storage)
- 구현 Issue·PR: 미등록

공모전·팀·공개 사람 탐색과 팀장의 지원자 검토를 기존 FastAPI 서비스에 연결합니다. 이 문서는 확정된 요구사항에서 실행 구조·API·저장 경계·검증 계획을 도출합니다. 사용자 동작은 기능 명세, 전송 필드는 API 문서, 물리 스키마는 DB 문서에서 관리합니다.

## 확정한 범위와 설계 제안

| 항목 | 결정과 근거 | 상태 |
| --- | --- | --- |
| 에이전트 기반 | `create_agent` 사용. Python 진입점은 `langchain.agents.create_agent`이며 LangGraph 런타임에서 실행 | 사용자 선택, 정확한 패키지 경로는 공식 문서 확인 |
| LLM | OpenAI Luna. 공식 API 모델 ID `gpt-6-luna` 사용 | 사용자 선택, 모델 ID는 공식 문서 확인 |
| 답변 전달 | 생성되는 답변을 실시간으로 표시 | 사용자 확정 |
| 현재 대화 유지 | 현재 브라우저 탭의 메모리에서 유지. 새로고침·탭 종료 시 초기화 | 사용자 확정 |
| 화면 이동 | 같은 브라우저 탭의 앱 화면·상세 이동에서는 대화·초안 유지. 새 대화·로그아웃 시 제거 | 기존 명세와 이번 결정 연결 |
| 전송·실행 | POST 요청의 SSE 응답, FastAPI에서 비동기 실행 | 이 문서의 제안 |
| 답변 생성 | 도구 조회·구조화된 후보 선정 → 서버 검증 → 답변 생성·스트리밍 | 이 문서의 제안 |
| 실행 상태 저장 | PostgreSQL에 제한된 실행 메타데이터를 저장 | 검토 필요: 필드·보존 기한·정리 방식 미정 |

이번 범위는 기존 추천 명세의 대화·일반 추천·지원자 검토·후보 추천입니다. Deep Agents, 자율적인 하위 에이전트, 외부 웹·포트폴리오 수집, 자동 지원·선발, 과거 대화 목록은 도입하지 않는 안을 제안합니다. 검색용 벡터 DB·임베딩·장기 기억도 현재 요구사항으로 확정하지 않습니다.

공식 문서의 지원 여부와 우리 앱에서의 호환성 검증은 다릅니다. 패키지 버전·도구 호출·구조화 출력·취소·스트리밍 조합은 구현 전 작은 연동 검증으로 확인하고 `pyproject.toml`·`uv.lock`에 고정합니다. 현재 코드에 LangChain 연동이 구현됐다는 의미는 아닙니다.

## 사용자 동작과 완료 기준

1. 로그인한 사용자가 입력하면 사용자 메시지를 한 번 추가하고 준비 상태를 표시합니다.
2. 현재 권한으로 자료를 찾는 동안에는 짧은 진행 상태를 표시합니다. 사용자에게 보여 줄 답변 생성이 시작되면 텍스트를 순차 표시합니다.
3. 검증된 최종 결과를 받으면 추천 카드·근거와 함께 완료 상태로 전환합니다. 일반 대화의 카드 합계는 최대 3개이며 지원자 후보 수의 제한으로 확대하지 않습니다.
4. 중단·실패·빈 결과를 구분합니다. 실패 재시도는 같은 사용자 메시지를 사용하고, 중단된 실행의 늦은 결과는 반영하지 않습니다.
5. 현재 탭에서 다른 화면에 다녀와도 대화·초안을 유지합니다. 새로고침·새 탭·탭 종료·새 대화·로그아웃 뒤 과거 대화를 복원하지 않습니다.

단계 2의 진행 상태는 모델의 내부 추론이 아닙니다. 전체 답변을 만든 뒤 글자를 지연 표시하는 모의 스트리밍은 완료 조건을 충족하지 않습니다. 확정 동작과 제품 예외는 [추천 명세](../specs/matching.md#acceptance-criteria)가 원본입니다.

## 실행 구조 제안

```text
브라우저: 현재 탭 대화·초안 + fetch 스트림 + AbortController
    │ POST 요청 / SSE 응답
FastAPI 라우터: 인증·CSRF·요청 검증·이벤트 직렬화
    │
AI 서비스: 목적 선택·실행 상태·취소·현재 권한·결과 검증
    ├─ create_agent: 허용된 조회 도구 → 구조화된 후보·근거 참조
    │      └─ 기존 도메인 서비스 → repositories → PostgreSQL
    ├─ 서버 검증: 실제 대상·관계·최신 상태·근거 범위
    └─ 답변 작성: Luna → 텍스트 조각 → 공개 범위 재확인 → SSE
```

첫 버전은 HTTP 연결을 유지하는 동안 요청 프로세스에서 실행합니다. 큐·별도 worker·LangGraph 서버를 선행 도입하지 않는 제안입니다. 배포 프록시의 응답 버퍼링과 연결 제한 시간은 실제 스트리밍을 확인해야 합니다. 프로세스 종료 후 자동 재개나 연결 복구를 보장하지 않으며, 그런 요구가 생기면 작업 큐와 재생 가능한 이벤트 저장을 별도로 설계합니다.

### 목적별 에이전트와 도구

서버가 요청 목적과 권한에 따라 설정을 고릅니다. 모델이 권한이나 목적을 바꾸거나 다른 에이전트로 임의 위임하지 않습니다. 같은 팩토리와 모델을 사용하되 시스템 지시·도구 집합·출력 스키마를 구분합니다.

| 목적 | 허용할 조회 | 서버가 지킬 경계 |
| --- | --- | --- |
| `chat` | 공개 공모전·팀·공개 사람 검색/상세 | 비공개 본인 프로필을 자동 사용하지 않음. 지원자의 비공개 정보에 접근하지 않음 |
| `applicant_review` | 현재 팀장이 받은 특정 지원·최신 프로필 | 요청 대상 한 건에 고정. 지원 후 비공개·종결 상태여도 기존 열람 정책 적용 |
| `applicant_recommendation` | 자기 팀 지원 목록·현재 프로필 | 새 후보는 유효한 지원 완료·검토 중이며 같은 공모전 소속이 없는 지원자 |

도구는 SQL 실행기나 HTTP 범용 호출기가 아닌 허용된 조회 함수입니다. 계정 ID·세션·팀장 권한·고정된 검토 대상은 서버 실행 컨텍스트로 주입하고 모델 인자로 선택하게 하지 않습니다. 프로필 소개·공고 본문·지원 메시지는 데이터로 취급하며 그 안의 지시가 도구·권한을 바꾸지 못하게 합니다.

기존 서비스의 반환 DTO 전체를 모델로 보내지 않습니다. 전송용 허용 필드 목록을 별도로 검토하고, 인증 값·연락 수단·외부 포트폴리오 내용은 포함하지 않습니다. 도구 실행마다 현재 권한을 검사하며 대화에서 보유한 ID도 다시 검증합니다.

### 후보 선정과 답변 생성

`create_agent`의 결과는 실제 리소스 ID와 근거 참조를 포함하는 내부 구조화 출력으로 받는 안입니다. 서버가 자료 존재·접근 권한·현재 후보 조건·카드 수를 검증한 뒤, 검증된 자료만으로 Luna에 사용자용 답변 작성을 요청합니다. 이 작성 단계는 도구 없는 추가 모델 호출입니다. 후보 선정 자체도 여러 번 모델을 호출할 수 있으므로 전체 비용을 두 번의 호출로 고정해서 계산하지 않습니다.

이 구조는 검증 전 후보·도구 인자·원시 JSON이 사용자 스트림에 섞이지 않게 하지만, 첫 텍스트까지의 지연과 추가 비용이 있습니다. 도구 조회 중에는 `progress`를 표시합니다. 제목·식별자·링크·`isDemo`·프로필 버전은 서버 자료로 조립하고 모델이 결정하지 않습니다. 구조화 출력 성공만으로 설명의 사실성까지 검증됐다고 보지 않으며 평가 사례로 확인합니다.

빈 결과는 서버가 빈 후보와 조건 수정 안내로 구성할 수 있습니다. 도구 장애·권한 상실·출력 파싱 실패를 빈 결과로 바꾸지 않습니다. 지원자 검토·추천은 지원 상태·소속·정원·알림을 변경하지 않습니다.

## 스트리밍과 실행 수명

SSE를 사용하는 전송 검토안과 이전 polling 초안의 관계는 [AI 전송 계약](../api/ai.md#streaming-proposal)에서 관리합니다. 프론트는 JSON 본문·쿠키·CSRF 헤더를 전달하는 `fetch`와 `ReadableStream`을 사용합니다. 하나의 네트워크 청크가 하나의 이벤트라고 가정하지 않고 UTF-8·줄 경계를 누적 파싱합니다.

일반 흐름은 `started → progress → answer.delta → result → done`입니다. 실패·중단·권한 변경은 각각 별도 종료 이벤트로 구분합니다. `done` 전에 연결이 끊기면 성공으로 표시하지 않습니다. 스트림 시작 전 오류는 기존 JSON HTTP 오류, 시작 후 오류는 SSE 이벤트로 전달하며 HTTP 상태를 뒤늦게 바꾸지 않습니다.

`conversationId`는 브라우저 탭의 대화 구분자, `clientMessageId`는 사용자 메시지 중복 방지, `requestId`·`attempt`는 실행과 재시도를 구분합니다. 이 값은 인증 수단이 아니며 서버 소유권 검사와 함께 사용합니다. 클라이언트는 현재 대화·요청·시도와 일치하는 이벤트만 반영합니다.

한 대화의 실행 하나와 현재 시도만 결과를 확정할 수 있게 합니다. 취소·완료 경쟁은 같은 실행 상태에 대한 원자적 전이로 처리하고 이전 시도가 새 시도를 종료하지 못하게 합니다. 여러 API 프로세스가 동일 상태를 확인해야 하므로 프로세스별 메모리만으로 중복·취소 제어를 완성하지 않습니다. 공유 저장소·장애 시 실행 만료·응답 유실 시 조회/재시도 계약은 D-03에서 결정합니다.

사용자 중단은 취소 요청과 스트림 닫기를 함께 수행하고, 연결 종료도 서버에서 감지해 하위 작업 취소를 요청합니다. 로그아웃·새 대화는 화면 상태를 즉시 제거하고 늦은 이벤트를 버립니다. 탭 종료 시 별도 취소 요청의 전달을 보장할 수 없으므로 연결 감지와 서버 실행 제한 시간이 필요합니다. 취소가 제공자의 계산·과금·로그 삭제까지 즉시 보장하는 것은 아닙니다.

## 현재 권한과 대화 맥락

일반 사람 추천은 현재 공개 범위를 따르고, 지원받은 팀장의 최신 비공개 프로필 검토 예외는 해당 요청에만 적용합니다. [기존 결과 재검증](../api/ai.md#current-permissions)을 스트리밍에서도 유지해야 합니다.

- 도구 입력 시점, 답변 작성 직전, 클라이언트로 내용을 내보내는 시점에 현재 세션·대상 접근 범위를 확인합니다. 검증에 실패하면 추가 전송을 멈추고 해당 답변 전체를 정보 변경 안내로 교체합니다.
- 답변에 비공개 정보가 포함될 수 있으므로 카드만 숨기는 처리는 충분하지 않습니다. 이미 전송된 바이트를 회수할 수 없으며 마지막에 한 번 검사하는 설계로 노출을 막았다고 주장하지 않습니다.
- 권한 변경과 전송의 경쟁을 어떻게 제한할지, 재검사 단위와 DB 부하를 어떻게 조절할지는 D-02의 선행 설계입니다. 단순한 주기적 검사만으로 공개 철회 즉시 적용을 충족한다고 간주하지 않습니다.
- 화면 재진입·복사는 서버의 현재 권한 재검증을 거칩니다. 저장된 본문 없이 검증할 참조·버전과 위변조 방지 방법, 응답 계약은 D-02·03에서 확정합니다. 실패 시 기존 본문을 복사하지 않습니다.

브라우저가 보낸 대화는 신뢰할 수 없는 입력입니다. 모델용 `system`·`developer`·`tool` 메시지나 도구 실행 결과를 클라이언트에서 받지 않습니다. 이전 사용자 조건과 결과 참조를 재구성하되, 서버가 조회한 최신 자료만 사실 근거로 사용합니다. 클라이언트가 돌려준 assistant 본문을 검증된 과거 결과로 인정하지 않습니다.

과거 대화를 통째로 재전송하면 공개 철회된 정보가 다시 모델 입력에 포함될 수 있습니다. 사용자 발화와 서버가 검증 가능한 결과 참조 중심의 요청 스키마를 우선 검토합니다. 참조 서명 또는 짧게 보관하는 서버 참조 기록의 선택, 자유 텍스트에 이미 복사된 정보를 다룰 한계는 D-02에서 명시합니다. 대화 길이·검색 후보·도구 호출의 예산도 D-04에서 정하며 1,000자 메시지 제한을 전체 컨텍스트 상한으로 오해하지 않습니다.

| --- | --- | --- |
| 브라우저 메모리 | 현재 대화·초안·표시 결과·진행 상태 | 새로고침·탭 종료·새 대화·로그아웃 시 제거. 대화 복원을 위해 localStorage·sessionStorage·IndexedDB에 저장하지 않음 |
| 요청 실행 메모리 | 필요한 대화 맥락·조회 자료·도구 메시지·작성 중 답변 | 해당 실행 동안만 사용하고 사용자 간 공유 금지 |
| 공유 실행 저장소 제안 | 소유 세션·요청 식별자·시도·상태·제한 시각·검증 참조 | 중복·취소·현재 권한 검증 목적. 필드·보존 기한·정리는 미정 |
| 앱 로그·관측 제안 | 요청 추적값·목적·모델·단계별 지연·토큰 사용량·안전한 오류 코드 | 대화·프로필·도구 원문을 기본 로그나 외부 tracing에 기록하지 않음. 보존 기한은 미정 |

현재 대화는 서버에 복원용 본문을 저장하지 않는 안입니다. 이것과 지원자 검토 결과의 별도 보존 요구는 구분합니다. 이전 API의 최신 검토 조회를 유지할지, 현재 탭 결과의 재검증만 제공할지는 D-03에서 정하며 현재 대화 결정만으로 지원자 결과의 영속화를 확정하지 않습니다.

LangGraph 영속 checkpointer·장기 store는 첫 버전에 연결하지 않는 안입니다. `create_agent`를 쓴다고 자동으로 PostgreSQL 대화 기록이 생기지 않으며, 앱 프로세스의 공유 에이전트 객체에 사용자별 메시지를 쌓지 않습니다.

OpenAI 연결은 `langchain-openai`의 `ChatOpenAI`, `model="gpt-6-luna"`, `use_responses_api=True`를 제안합니다. Responses API를 명시하고 `store=False`로 호출하는 구성을 연동 검증합니다. API 키는 서버 설정으로만 읽습니다. 다른 모델로 자동 전환하지 않으며 reasoning 강도·출력 한도는 D-04에서 정합니다. [Luna 모델 문서](https://developers.openai.com/api/docs/models/gpt-6-luna), [ChatOpenAI 통합 문서](https://docs.langchain.com/oss/python/integrations/chat/openai)

OpenAI의 응답 저장 옵션과 서비스의 대화 저장 정책은 별개입니다. `store=False`를 제공자의 모든 로그·보존이 없다는 의미로 설명하지 않습니다. 실제 전송 필드와 조직의 데이터 설정은 [OpenAI 데이터 정책](https://developers.openai.com/api/docs/guides/your-data)에 맞춰 D-01에서 확인합니다.

## 코드 책임과 기존 계약

아래 AI 파일은 **생성 예정**입니다. 현재 [계층 규칙](../development/architecture.md#responsibility-boundaries)을 유지하며 `agents`를 LLM 연동 계층으로 추가하는 제안입니다.

| 파일·영역 | 책임 |
| --- | --- |
| `backend/app/routers/ai.py` | HTTP 요청·인증/CSRF 의존성·SSE 응답·연결 종료 전달 |
| `backend/app/schemas/ai.py` | 요청·결과·이벤트 DTO. ORM 의존 없음 |
| `backend/app/services/ai.py` | 목적별 실행·소유권·취소·현재 상태·결과 조립. FastAPI 객체 의존 없음 |
| `backend/app/agents/factory.py`, `prompts.py` | 목적별 `create_agent`·Luna 설정·시스템 지시 |
| `backend/app/agents/tools.py` | 허용된 조회 어댑터·모델 전송 필드 최소화 |
| `backend/app/agents/streaming.py` | 모델 스트림을 내부 타입 이벤트로 변환. SSE 형식은 라우터에서 직렬화 |
| `backend/app/models/ai_runs.py`, `repositories/ai_runs.py` | D-03에서 공유 실행 저장을 채택할 때만 추가. 모델·SQL·원자적 상태 갱신 |
| `frontend/src/features/ai/` | 기존 화면을 탭 메모리 상태·실제 스트림·취소·재시도에 연결 |

의존 방향은 `routers → services/ai → agents → 기존 도메인 services → repositories`로 제안합니다. `agents`가 `services/ai`를 역으로 import하지 않으며 실행 컨텍스트·내부 결과 타입으로 연결합니다. 도구 병렬 실행 시 각각 독립된 짧은 `AsyncSession`을 열고, 열린 세션이나 트랜잭션을 모델 응답 대기 동안 유지하지 않습니다. 요청 의존성의 세션 하나를 병렬 도구에 공유하지 않습니다.

| 기존 원본·심볼 | 사용할 계약 |
| --- | --- |
| [인증 의존성](../../backend/app/dependencies/auth.py) `get_current_session` | 검증된 `SessionPrincipal`을 받아 계정·인증 맥락을 실행에 고정 |
| [공모전 서비스](../../backend/app/services/contests.py) | `list_contests(session: AsyncSession, query: ContestSearch) → Page[ContestSummary]`, `get_contest_detail(session, contest_id: UUID) → ContestDetail` |
| [프로필 서비스](../../backend/app/services/profiles.py) | `list_people(session: AsyncSession, query: PeopleQuery) → Page[PersonSummary]`, `get_public_profile(session, account_id: UUID) → ProfileResponse`. 공개 자료만 조회 |
| [팀 서비스](../../backend/app/services/teams.py) | `list_teams(session: AsyncSession, search: TeamSearch) → Page[TeamSummary]`, `get_team_detail(session, team_id: UUID) → TeamDetail`. 신규 지원 추천 조건은 추가 검증 |
| [지원자 서비스](../../backend/app/services/application_review.py) | `list_applicants(session: AsyncSession, team_id: UUID, account_id: UUID, query: ApplicantSearch) → Page[ApplicantResponse]`, `get_applicant(session, application_id: UUID, account_id: UUID) → ApplicantResponse`. 현재 팀장 관계 검사 |

표는 이 계획에서 사용하는 필수 인자이며 선택 인자는 연결된 원본을 따릅니다. 기존 목록 함수가 모든 추천 조건을 검사한다고 가정하지 않습니다. 동일 공모전 소속·미선발 이력 등 신규 지원 후보 조건은 [추천 정책](../specs/matching.md#eligibility)에 맞춰 서비스에서 보완합니다. 모델은 DB 세션·ORM 객체를 받지 않습니다.

## 구현 순서와 검증 계획

다음은 후속 작업 계획이며 이번 문서 변경에서 실행한 구현·테스트 기록이 아닙니다. 각 단계의 선행 결정을 반영한 뒤 구현 계획을 확정합니다.

| 순서 | 작업과 출력 | 선행 조건 | 검증할 결과 |
| --- | --- | --- | --- |
| 1 | 허용 입력 필드·재검증·저장·제한 정책을 명세/API/DB 원본에 반영 | D-01~04 | 권한·스트림·복사·재시도 계약 사이에 미정 분기나 충돌이 없음 |
| 2 | Luna + `create_agent`의 비동기 도구·구조화 출력·스트림 연동 검증, 의존성 고정 | 호출 설정·전송 필드 결정 | 도구 호출 뒤 검증 가능한 출력, 실제 델타, 취소 전파. 실제 키가 필요한 검증은 키 설정 후 별도 수행 |
| 3 | 목적별 조회 도구·결과 검증·실행 상태 구현 | 1·2, 필요 시 DB migration | AC-17~21·24·27~32: 권한 우회 없음, 실제 ID·최신 후보만 반환, 지원 상태 불변 |
| 4 | 스트리밍 라우터·중단·재시도·재검증 API 구현 | 3, 전송 계약 | AC-22·25·33: 시작 전 HTTP 오류와 시작 후 이벤트 오류 구분, 세션 만료·연결 단절·경쟁 처리 |
| 5 | [AI 화면](../../frontend/src/features/ai/AiChatPage.tsx) 연결, 모의 응답 경로 분리 | 4 | AC-16·23·26·28·34: 실시간 표시·카드 수·이동 유지·새로고침 초기화·늦은 응답 차단 |
| 6 | 통합 시나리오·품질·운영 한도 확인, 문서 구현 상태 갱신 | 3~5 | 실제 정책·권한·현재 프로필·중단·빈 결과·실패를 구분하고 결과 근거와 연결 대상 일치 |

도구·권한·동시성 테스트는 가짜 모델과 실제 DB로 재현할 수 있게 하고, 모델 품질 평가는 별도 사례로 관리합니다. 라이브 모델 평가를 일반 테스트의 유일한 성공 기준으로 두지 않습니다. 구현 시 [테스트 규칙](../development/testing.md)을 따릅니다.

필수 경계 사례는 비로그인, 세션 만료, 다른 팀 지원자 ID, 일반 추천의 비공개 전환, 지원 후 비공개 전환된 자기 팀 지원자, 선발·취소·폐기 경쟁, 프로필 버전 변경, 존재하지 않는 모델 출력 ID, 도구·제공자 실패, 중복 전송·재시도, 취소와 완료 경쟁, 새 대화 후 늦은 이벤트입니다. 프론트는 분할 UTF-8/SSE 프레임과 종료 이벤트 없는 연결 끊김도 확인합니다.

## API·DB 영향

AI API는 아직 미구현이므로 운영 API의 마이그레이션은 없습니다. 다만 이전 `202 + Location + polling` 계약은 스트리밍 설계로 대체해야 하며 현재 대화 GET 복원도 채택하지 않습니다. 결과 DTO·권한 정책은 계속 활용하고, 기존 앵커는 과거 문서 참조를 위해 남깁니다. 새 계약은 [AI API](../api/ai.md#streaming-proposal)에 정리합니다.

이번 변경은 테이블·마이그레이션을 추가하지 않습니다. 공유 실행 저장을 채택하면 [DB 설계](../database/decisions.md#ai-storage)에 필드·제약·소유 세션·정리 정책을 먼저 작성하고 모델→migration→실행 제어 순서로 구현합니다. 메시지 원문·프로필 사본·벡터 테이블을 식별자 필요만으로 추가하지 않습니다.

## 기술 근거

2026-10-25 확인한 공식 문서입니다. 패키지 버전과 옵션의 실제 조합은 단계 2에서 다시 검증합니다.

- [LangGraph 영속화](https://docs.langchain.com/oss/python/langgraph/persistence): checkpointer·store와 앱의 저장 정책을 명시적으로 선택.
