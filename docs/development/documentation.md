# 문서 관리와 Wiki 게시

## 원본과 편집

- 사람과 에이전트에게 전달하는 작업 지침·명세·개발 정보는 `docs/`에서 관리합니다. 루트 `AGENTS.md`는 문서 인덱스로 들어오는 링크만 유지합니다.
- `docs/README.md`와 하위 폴더의 `README.md`는 짧은 인덱스입니다. 문서의 목적과 언제 읽을지를 안내하고 본문 내용을 반복하지 않습니다.
- 새 문서를 만들면 관련 인덱스에 연결합니다. 작업에 필요한 문서만 읽을 수 있도록 한 문서에 모든 영역의 규칙을 합치지 않습니다.
- Wiki는 `main`의 게시본입니다. 수정은 저장소 PR로 제안합니다. Wiki를 직접 고치면 다음 게시에서 덮어쓸 수 있습니다.
- PR 템플릿은 변경·검증 정보를 수집하는 양식이며, 실제 작업 규칙은 [팀 작업 흐름](workflow.md)을 참조합니다.

## 링크와 게시 형식

- 저장소 내부 링크는 현재 문서 기준 상대 경로로 씁니다. Markdown 페이지, 이미지와 일반 파일을 구분합니다.
- 내부 파일과 일반 Markdown 제목 앵커를 검사합니다. 외부 URL의 접속 가능 여부는 검사하지 않습니다. 로컬 HTML 링크 대신 Markdown 링크를 사용합니다.
- 코드 예시는 fenced code block 안에 둡니다. 설명의 파일명과 명령은 실제 파일·설정에 맞춥니다.
- `docs/README.md`는 Wiki의 `Home`이 되고, 나머지 페이지는 전체 상대 경로를 이용한 고유 이름을 가집니다. `_Sidebar`와 원본 링크는 자동 생성합니다.
- 게시용 `.wiki-build/`는 임시 결과물이며 커밋하지 않습니다. 문서를 두 위치에서 수동으로 수정하지 않습니다.
- 공개 저장소의 Wiki도 공개됩니다. 실제 비밀값·팀원의 개인정보·내부 계정 정보는 문서에 넣지 않습니다.

## 자동화

1. PR에서 문서 링크, 페이지 이름 충돌, 게시 변환과 변환기 테스트를 검사합니다.
2. `main`에 변경이 병합되면 GitHub Actions가 Wiki 페이지를 생성합니다. 코드만 바뀐 경우에도 최신 원본 커밋을 일치시킵니다.
3. 생성한 페이지를 같은 저장소의 `wejo-app.wiki.git`에 반영합니다. PR 초안은 게시하지 않습니다.
4. Wiki의 원본 커밋 링크로 어떤 변경이 게시되었는지 확인합니다. 게시 실패는 Actions에서 확인하고 원인 수정 후 재실행합니다.

게시에는 AI, 별도 서버, 장기 보관 아티팩트가 필요하지 않습니다. 표준 GitHub 호스팅 러너를 사용합니다. Wiki 최초 페이지는 GitHub UI에서 한 번 생성해야 Git 저장소가 초기화됩니다.

## 로컬 검사

저장소 루트에서 Python 3.13 이상으로 실행합니다.

```bash
python3 -m unittest discover -s scripts/tests -v
python3 scripts/export_wiki.py --repository wejo-team/wejo-app --ref HEAD
```

생성 결과는 `.wiki-build/`에서 확인합니다. 실제 게시 주소에는 커밋 SHA를 사용하며 CI가 이를 전달합니다.
