# 팀 작업 흐름

새 기능과 중요한 정책 변경은 **명세 작성 → 사람 검토·확정 → 개발 계획 → 구현·검증 → 결과 리뷰** 순서로 진행합니다. 별도 SDD 도구 없이 Markdown과 GitHub PR을 사용합니다.

GitHub가 처음인 팀원은 [문서 협업 시작하기](../collaboration/README.md)에서 브라우저로 작성·검토하는 방법을 확인합니다. 이 문서는 팀 공통 절차와 병합 기준을 관리합니다.

## 브랜치와 릴리스 흐름

기본 브랜치는 `develop`입니다. 최신 `develop`에서 `feat/…`, `fix/…`, `docs/…` 같은 [작업 브랜치](conventions.md)를 만들고, 명세·기능·수정 PR의 대상도 `develop`으로 지정합니다. 작업 브랜치를 뜻하는 `feature/*` 대신 저장소의 `<type>/<작업-내용>` 이름을 사용합니다.

| 변경 | PR 방향 | 병합 방식 | 병합 후 실행 |
| --- | --- | --- | --- |
| 명세·기능·수정 | 작업 브랜치 → `develop` | Squash merge | 전체 CI, 운영 배포 없음 |
| 운영 릴리스 | 같은 저장소의 `develop` → `main` | Merge commit | 전체 CI 성공 후 운영 CD |
| 릴리스 이력 동기화 | 같은 저장소의 `main` → `develop` | Merge commit | 전체 CI, 운영 배포 없음 |
| 동기화가 늦어진 경우 | `develop` 기반 `chore/sync-main-<sha>` → `develop` | Merge commit | 전체 CI, 운영 배포 없음 |

`main`으로 직접 보내는 작업 PR은 허용하지 않습니다. 수정도 `develop`에 먼저 반영하고 릴리스 PR로 운영에 전달합니다. 외부 fork의 작업 브랜치는 `develop`을 대상으로 할 수 있지만, `develop` → `main`과 `main` → `develop` PR은 같은 저장소의 브랜치 사이에서만 엽니다. 지연 동기화 절차는 아래 병합 방식에서 확인하며, 다른 대상 브랜치는 `PR conventions`에서 거부합니다.

릴리스 PR에는 포함한 변경과 검증·마이그레이션·복구 영향을 정리합니다. `main`의 CI가 성공한 같은 SHA만 [운영 CD](continuous-deployment.md)로 배포합니다. `develop` 병합, PR 검사 통과, `main` 병합은 각각 운영 배포 성공과 구분해 기록합니다. 문서 사이트는 `main`의 문서 검증 성공 후에만 게시합니다.

## 1. 명세 PR

- [명세 템플릿](../templates/spec.md)을 복사해 `docs/specs/<feature>.md`를 작성하고 [명세 인덱스](../specs/README.md)에 추가합니다.
- 목적, 사용자 흐름, 동작·정책, 예외, 범위 밖 항목, 관찰 가능한 완료 조건을 적습니다. 이 단계에서 상세 구현 계획을 함께 확정하지 않습니다.
- 미정 사항을 표시하고 명세만 포함한 PR을 엽니다. 서비스 동작을 책임지는 팀원이 내용에 합의하고, 개발자가 기술적으로 가능한지 검토합니다.
- 작성자 외 팀원의 GitHub 리뷰와 병합 기록을 합의의 근거로 남깁니다. 중요한 미정 사항이 해결된 뒤 병합합니다.

## 2. 개발 계획

- 병합된 명세를 기준으로 프론트·백엔드 작업, API·DB 영향, 순서, 검증 방법을 정합니다.
- 계획은 연결된 구현 Draft PR 본문에 둡니다. 길어서 별도 문서가 필요할 때만 `docs/development-plans/`를 추가하고 인덱스에 연결합니다.
- 필요한 설계 리뷰를 진행한 후 구현합니다. 요구사항 자체가 바뀌면 먼저 명세 변경을 다시 검토합니다.
- 아직 코드 변경이 없어 PR을 만들 수 없다면 연결된 GitHub Issue에 계획을 작성하고, 구현 PR을 열 때 링크합니다.

[개발 계획 템플릿](../templates/development-plan.md)을 필요한 항목만 남겨 사용합니다. 계획에는 기준 명세와 완료 조건, 작업별 수정 범위·선행 작업·사용하거나 제공하는 계약, API·DB 영향, 검증 방법을 적습니다. 작은 수정은 PR 본문 몇 줄로 충분하며, 모든 작업에 별도 계획 파일을 만들지는 않습니다.

계약은 실제 원본 파일·심볼을 연결하고 필요한 정확한 이름·입출력 타입을 명시합니다. 구현 전인 계약은 계획에서 미구현임을 표시합니다. 프론트와 백엔드가 같은 계약을 사용하는 경우 계약과 작업 순서를 먼저 맞춥니다. 기술 규칙과 schema 전체를 계획에 복제하지 않습니다.

### 작업 분할과 인계

사람 또는 에이전트에게 작업을 나누거나 다음 세션으로 넘길 때는 기존 계획·Issue·PR에 아래 정보를 남깁니다. 별도의 상태 문서를 중복 생성하지 않습니다.

- **근거와 목표:** 명세·계획 링크, 담당 완료 조건 번호, 적용할 지침의 경로·절.
- **수정 범위:** 담당 파일·심볼, 이번 작업에서 다루지 않을 범위, 선행 작업과 이미 정한 결정.
- **계약:** 사용하는 입력과 제공할 출력의 원본 위치·이름·타입, 다른 작업과 맞춰야 할 부분.
- **검증과 상태:** 수행할 검사·기대 결과, 완료한 변경과 커밋, 실제 검사 결과, 남은 작업·막힌 점.

인계받는 사람이나 에이전트는 현재 브랜치·diff와 기록을 확인해 이어서 작업합니다. 계획과 구현이 다르면 차이와 영향을 기록하고, 요구사항 변경은 명세 검토 절차를 따릅니다.

## 3. 구현과 결과 리뷰

- 기능과 관련 테스트를 구현하고 [테스트·CI](testing.md)의 해당 검사를 실행합니다.
- PR에는 명세 링크, 완료 조건별 결과, UI 변경 시 확인 자료, 미실행 검사와 이유를 적습니다.
- 완료 조건은 명세의 번호로 연결합니다. 예를 들어 `AC-01`에 대응하는 테스트·실행 결과를 적고, 확인하지 못한 조건은 미확인으로 남깁니다. 명세가 없는 작은 수정은 수정 목표와 검증 근거를 직접 적습니다.
- 리뷰어는 코드뿐 아니라 명세의 정상·실패 경로 충족 여부를 확인합니다.
- 구현 PR에서 명세의 구현 상태와 실제 동작 설명을 함께 갱신합니다. CI가 통과하고 필요한 리뷰를 마친 뒤 병합합니다.

## 상태와 변경 범위

- 명세의 구현 상태는 `예정 / 진행 중 / 완료`입니다. 승인 근거는 명세 PR, 구현 근거는 구현 PR에 남깁니다.
- `develop`에 병합된 명세는 팀의 합의 내용을 포함하며, 아직 구현되지 않은 기능도 있습니다. `완료`는 병합된 코드와 검증을 뜻하고 운영 배포를 뜻하지 않습니다. `main`과 문서 사이트에는 릴리스에 포함된 문서가 게시됩니다.
- 새 기능·중요한 정책 변경은 명세 PR과 구현 PR을 나눕니다. 오탈자, 작은 버그 수정, 합의된 초기 실행 기반·도구 설정은 목적에 맞는 하나의 PR로 진행할 수 있습니다.
- 사용자가 특정 작업의 구현·병합을 명시적으로 허용했다면 그 범위의 승인으로 취급합니다. 추가 승인을 반복 요청하거나 에이전트가 사람의 리뷰를 했다고 기록하지 않습니다. GitHub의 보호 규칙과 명시적으로 허용된 리더 예외를 따릅니다. 에이전트가 자체 판단으로 보호 규칙을 해제하지 않습니다.

## 병합 방식

작업 PR은 **Squash merge**로 `develop`에 병합합니다. 작업 브랜치에서는 목적별로 작은 커밋을 만들고, `develop`에는 작업 PR 하나를 커밋 하나로 남깁니다. 팀원이 기능·변경 단위로 이력을 읽고 되돌리기 쉽도록 한 작업 PR은 한 목적을 유지합니다.

- `develop` → `main` 릴리스와 `main` → `develop` 동기화는 **Merge commit**으로 병합해 두 장기 브랜치의 공통 이력을 보존합니다. 아래의 지연 동기화 작업 브랜치도 같은 예외를 적용하며, 이 PR을 squash하거나 rebase하지 않습니다.
- 저장소에서는 Squash merge와 Merge commit을 허용하고 Rebase merge는 비활성화합니다. GitHub의 병합 방식 허용은 저장소 전체 설정이므로, 병합자는 PR 방향에 맞는 방식을 선택해야 합니다. `PR conventions`는 브랜치 방향을 검사하며 선택할 병합 방식까지 강제하지 않습니다.
- 병합 전 제목을 `type(scope): 설명` 형태로 정리하고 PR 설명에 최종 변경·검증 결과를 남깁니다. 릴리스·동기화 제목도 `chore(release): …`처럼 같은 형식을 사용합니다.
- 릴리스부터 동기화가 끝날 때까지 `develop`의 후속 작업 PR 병합을 잠시 보류합니다. 릴리스와 배포 결과를 확인한 뒤 `main` → `develop` 동기화 PR을 열어 merge commit으로 병합하고, 그 다음 작업 PR 병합을 재개합니다.
- 동기화가 늦어 `develop`에 후속 변경이 들어왔다면 최신 `develop`에서 `chore/sync-main-<sha>`를 만들고 이 작업 브랜치에 `origin/main`을 merge합니다. 충돌 해결·검사를 거친 뒤 `develop` 대상 동기화 PR을 **Merge commit**으로 병합합니다. 이 PR은 일반 작업 PR의 squash 규칙에서 제외하고, 본문에 동기화할 `main` SHA와 해결한 충돌을 적습니다.
- 최신 대상 브랜치 반영 조건을 맞추려고 동기화 PR의 `Update branch`로 원격 `main`에 미출시 `develop` 변경을 역병합하지 않습니다. 지연 동기화도 원격 `main` 직접 갱신·브랜치 강제 푸시 없이 위 작업 브랜치에서 해결합니다.
- Squash 이후의 다음 작업은 최신 `develop`에서 새 작업 브랜치를 만들어 진행합니다. `develop`과 `main`은 삭제하거나 강제 푸시하지 않으며, 기존 병합 이력을 다시 쓰지 않습니다.

## 자동 검사와 사람 리뷰

문서 CI는 링크·게시 변환을, 앱 CI는 포맷·정적 검사·테스트·빌드를 확인합니다. 요구사항의 타당성과 사용자 경험은 사람의 리뷰 대상입니다. 저장소의 병합 제한은 GitHub 설정에서 별도로 관리하며, 이 문서 자체가 제한을 활성화하지 않습니다.

`develop`과 `main`의 기본 병합 기준은 `Validate docs`, `Frontend`, `Backend`, `PR conventions` 검사 성공, 최신 대상 브랜치 반영, 작성자 외 1명 이상의 승인, 리뷰 대화 해결입니다. 새 변경이 올라오면 이전 승인은 해제합니다.

PR의 실제 테스트는 [변경 영향 범위](testing.md#ci-scope)에 따라 선택합니다. 필수 검사 이름은 유지하며, 앱 검사가 불필요한 경우에도 범위 판별 성공과 명시적 생략을 확인한 뒤 통과합니다. `develop`과 `main`의 push는 전체 CI를 실행하며, 운영 CD는 `main`의 성공한 CI에만 연결합니다.

프로젝트 리더 `jhpark324`는 GitHub의 PR 필수 요건 예외 사용자입니다. **승인이 없거나 `Request changes`가 남아 있어도 리더는 병합할 수 있습니다.** 일반 팀원은 승인 1명과 변경 요청 해소가 필요합니다. 예외는 해당 계정에만 적용하며, 관리자 전체에 대한 보호 규칙 적용은 유지합니다.

리더 예외로도 두 브랜치의 필수 CI 3개와 `PR conventions`·최신 대상 브랜치 반영·리뷰 대화 해결과 강제 푸시·브랜치 삭제 금지는 우회하지 않습니다. GitHub의 이 예외는 PR 없이 반영하는 것도 허용하지만, 팀의 작업 흐름은 리더도 위 방향의 PR을 사용하는 것으로 유지합니다.

### Request changes 처리

- 쓰기 권한 이상의 리뷰어가 `Request changes`를 남기면 일반 팀원은 병합할 수 없습니다. 다른 리뷰어가 승인 인원수를 채워도 해당 변경 요청은 별도로 해소해야 합니다.
- 작성자가 수정한 뒤 변경을 요청한 리뷰어에게 재검토를 요청하고, 그 리뷰어가 `Approve`하면 변경 요청이 해소됩니다.
- 새 커밋을 올리거나 코멘트를 `Resolve conversation`하는 것만으로 변경 요청이 해소되지는 않습니다. 리뷰 대화 해결과 변경 요청 해소는 각각 확인합니다.
- 리더가 변경 요청을 남긴 채 병합할 때는 요청 내용을 확인하고 판단 이유를 PR에 남깁니다. 리더 예외로 병합해도 해당 리뷰가 승인으로 바뀌는 것은 아닙니다.
- 리뷰어가 부재하는 등 리뷰를 기각해야 하는 예외 상황에는 권한 있는 사람이 이유를 기록하여 `Dismiss review`할 수 있습니다. 에이전트는 병합을 통과시키기 위해 임의로 리뷰를 기각하거나 보호 규칙을 변경하지 않습니다.

리더의 예외는 자기 PR에 승인 리뷰를 작성하는 권한이 아닙니다. 에이전트는 리더가 해당 PR의 병합을 요청했거나 이미 승인한 작업 범위에서만 사용하고, 실제 사람의 리뷰가 있었던 것처럼 기록하지 않습니다.

PR 양식은 [기본 PR 템플릿](../../.github/pull_request_template.md)을 사용합니다. 변경하지 않은 영역까지 검사를 수행하거나 해당 없는 항목을 사실처럼 체크하지 않습니다.
