# 구현 현황과 다음 작업

**기준: 2026-10-24, PR #123~#144 반영 및 #145 문서 정리.** 이 문서는 이번 백엔드 PR 묶음의 결과와 다음 개발 순서를 설명합니다. 이후 변경은 [API 인덱스](../api/README.md)와 연결된 코드·PR에서 확인합니다.

## 지금 어디까지 왔나요?

**DB 구조와 서버의 조회·지원 관리 기능을 갖췄습니다. 새 사용자가 가입해서 팀을 만들고 지원하는 전체 흐름은 아직 완성되지 않았습니다.**

- **서버:** 17개 테이블과 5개 마이그레이션, health를 포함한 29개 API 경로가 있습니다. 기존 데이터의 조회, 지원 검토·선발·취소, 모집 종료·재개, 알림 읽음 등을 처리합니다.
- **화면:** 로그인·탐색·프로필·팀·AI 화면을 시연할 수 있습니다. 현재 주요 화면은 브라우저 메모리의 예시 데이터를 사용하며 실제 업무 API 연결이 남아 있습니다.
- **검증:** PR마다 코드를 검토하고 최신 `main` 반영 후 필수 CI를 확인합니다. DB 검사는 CI의 PostgreSQL에서 실행하며, 화면 시연을 서버 연동 검증으로 계산하지 않습니다.
- **운영:** 실제 학사·공고·시연 데이터 적재와 서비스 운영 배포는 이번 작업에 포함하지 않았습니다. 문서 사이트 게시와 서비스 배포는 별개입니다.

수치는 [라우터 등록](../../backend/app/main.py), [모델 등록](../../backend/alembic/env.py), [DB 구현 범위](../database/README.md)를 기준으로 확인했습니다. 화면의 현재 데이터 처리 방식은 [App](../../frontend/src/app/App.tsx)과 [DemoProvider](../../frontend/src/features/demo/DemoProvider.tsx)에 명시되어 있습니다.

## 다음 작업은 어떤 순서가 좋나요?

**먼저 실제 계정으로 로그인하고 프로필을 저장할 수 있게 만드는 것이 권장 순서입니다.** 그다음 팀 생성·지원 접수를 연결하면 이미 구현한 검토·선발·취소 기능까지 한 흐름으로 검증할 수 있습니다.

| 순서 | 작업 | 완료되면 확인할 사용자 행동 |
| --- | --- | --- |
| 1 | 가입·로그인·아이디 중복 확인 API와 인증 화면 연결. 시도 제한·차단 목록 공급, 로컬 HTTPS·origin 설정 확정 | 가입 → 자동 로그인 → 새로고침 후 로그인 유지 → 로그아웃 |
| 2 | 실제 학사 데이터 준비, 프로필 저장·수정·공개 전환 API와 화면 연결. 일반 텍스트의 정규화·글자 수 기준 확정 | 프로필 작성 → 다시 조회 → 공개 전환 → 다른 계정의 조회 권한 확인 |
| 3 | 공고 목록·입력 CLI, 팀 생성·신규 지원 API. 팀 생성의 프로필 조건 확정 | 공고 선택 → 팀 생성 → 다른 계정으로 지원 → 팀장의 지원자 목록 확인 |
| 4 | 기존 조회·팀 공간·선발·취소·알림 화면을 실제 API로 연결하고 E2E 검증 | 선발 → 양쪽 계정에서 소속·알림 확인 → 취소 → 자리 반환·접근 종료 확인 |
| 5 | AI 기능의 제공자·후보 범위·데이터 보존을 결정하고 실제 구현 | 실제 계정의 허용된 데이터로 추천·지원자 검토 실행 |
| 6 | 운영 환경·키·데이터 적재·마이그레이션·관측·복구 절차를 준비하고 배포 검증 | 운영 주소에서 핵심 흐름과 실패 복구 확인 |

이는 권장 작업 순서이며 새로운 제품 정책을 확정한 목록은 아닙니다. 기능별 선행 결정은 [설계 검토 목록](../database/decisions.md#open-decisions), 이미 합의한 정책은 [기능 명세](../specs/README.md)를 따릅니다. API가 준비된 읽기 화면은 앞 단계와 함께 연결할 수 있습니다.

다음 기능의 완료 기준은 **화면 동작 + 서버 저장 + 다른 요청에서 재조회 + 권한·실패 처리 검증**으로 잡습니다. 메모리 상태 변경만으로 저장 완료를 표시하지 않도록 전환해야 합니다.

## 검증 범위와 확인 방법

- 필수 검사 `Backend`, `Frontend`, `Validate docs`의 성공과 최신 기본 브랜치 반영, 미해결 리뷰 대화 여부를 병합 전에 확인합니다. 영향이 없는 프론트 검사는 CI 규칙에 따른 명시적 생략일 수 있으며, `main`에서는 전체 검사가 실행됩니다.
- 백엔드 CI는 Ruff·mypy·pytest와 PostgreSQL 17.11의 마이그레이션 적용·모델 차이 검사를 수행합니다. 선발·취소·모집 변경은 동시 요청과 실패 시 롤백까지 검증합니다.
- 로컬에서는 DB 없이 실행할 수 있는 검사와 수정 회귀 테스트를 실행했습니다. 이 작업 환경에서는 Docker의 PostgreSQL을 사용할 수 없어 DB 통합 검증은 GitHub Actions 결과로 확인했습니다.
- 브라우저의 실제 가입→지원→선발 E2E, 실제 데이터 적재, 운영 DB 변경·배포는 수행하지 않았습니다. 구현되지 않은 진입 API와 화면 연동을 먼저 완성해야 합니다.

재현 명령은 [로컬 실행](local-development.md), 검사 범위는 [테스트·CI 기준](testing.md), 실행 결과는 [GitHub Actions](https://github.com/wejo-team/sku-dreamon/actions)에서 확인합니다.

## 코드를 읽을 때: 공통 기반과 `__init__.py`

ORM 모델은 [Base](../../backend/app/core/db/base.py)를 상속해 같은 `metadata`와 제약조건 이름 규칙을 사용합니다. PK·시각 컬럼은 [공통 타입](../../backend/app/core/db/types.py)과 [mixin](../../backend/app/core/db/mixins.py)을 필요한 곳에 조합합니다. 공유 PK와 복합 PK는 각 모델에서 직접 선언합니다.

`__init__.py`에서 다시 내보내지 않아도 `from app.core.db.base import Base`처럼 정의된 모듈에서 바로 사용할 수 있습니다. 현재는 [명시적 모듈 import 규칙](backend.md#orm-foundation)을 따릅니다. 패키지의 짧은 공개 import 경로가 필요해지면 `__init__.py`에 재노출할 수 있지만, ORM 모델 등록과는 다른 작업입니다. 마이그레이션의 모델 등록은 [alembic/env.py](../../backend/alembic/env.py)에서 확인합니다.
